# Tech Stack and Architecture for a Fast, Self-Hostable Engineering Knowledge Platform (ingestion + wiki + chat-with-data + compliance checking), as of October 2026

Research method note: ~70 web searches plus primary-source fetches. The sandbox egress proxy blocked most non-GitHub/non-Anthropic domains (openai.com, groq.com, together.ai, ai.google.dev, learn.microsoft.com, docs.aws.amazon.com, huggingface.co, arxiv.org, tigerdata.com, premai.io, redhat.com, etc.), so for those vendors the figures below come from search-result summaries of secondary trackers and are flagged as such. Anthropic's own pricing/retention docs and ~30 GitHub READMEs were read directly.

## Key Question 1: What stack would a seasoned team pick today for maximum speed/efficiency without sacrificing maintainability, and what is the evidence?

### Takeaway
The evidence points to a "boring core, fast edges" stack: Postgres as the single system of record (pgvector + pgvectorscale for ANN, ParadeDB/pg_search or Postgres FTS for BM25, Hatchet or pg-boss for queues), a thin typed API in Python (FastAPI/Litestar + Pydantic AI, or no framework) or TypeScript (Hono/Bun) with Python reserved for ML-side work, vLLM or SGLang for any self-hosted model serving, TEI for embeddings/rerankers, a React/Next.js (or SvelteKit) frontend with Tiptap + Hocuspocus (Yjs) for the collaborative wiki, Docker Compose on one GPU box until multi-node/autoscaling is genuinely needed, Langfuse or Phoenix via OpenTelemetry, DeepEval/promptfoo in CI, and Keycloak/Authentik/Zitadel for SSO. The benchmark evidence shows language choice matters far less than I/O design and retrieval quality for a RAG backend at 50-200 users; the GPU/LLM path and the vector index dominate latency.

### Cited Findings

#### (1) Backend language/framework
- A May 2026 analysis argues raw RPS says little about stack choice: "a backend that handles 8,000 RPS at peak runs equally well on FastAPI, Express, or Go, while one handling 80,000 RPS does not." — [index.dev](https://www.index.dev/skill-vs-skill/backend-go-vs-nodejs-vs-python-fastapi)
- A FastAPI-vs-Axum head-to-head (both in Docker) found Axum only ~6% faster with the load client as the bottleneck; the author notes other sources report Axum ~5x faster and that for a new project he'd still pick Axum/Rust for memory/type safety and smaller images. — [zachcoleman/fastapi-vs-axum](https://github.com/zachcoleman/fastapi-vs-axum/blob/main/README.md)
- A vendor guide claims FastAPI is comparable to Node for CRUD but 30-40% slower than Go under heavy load (no methodology shown). — [acquaintsoft](https://acquaintsoft.com/blog/fastapi-vs-nodejs-vs-go-performance-benchmarks)
- WWT benchmark: Bun and Go close on RPS; Go clearly best on memory. Hello-world Bun/Express outperforms FastAPI "by a high margin" but with high memory use. — [WWT](https://www.wwt.com/blog/performance-benchmarking-bun-vs-c-vs-go-vs-nodejs-vs-python); [Medium](https://medium.com/deno-the-complete-reference/hello-world-performance-bun-express-vs-python-fast-api-dc3c00960981)
- Litestar (MIT, ~8.5k stars) claims to be "on par with, or significantly faster than comparable ASGI frameworks," using msgspec for serialization/validation. — [litestar-org/litestar](https://github.com/litestar-org/litestar)
- Python 3.14 free-threaded build: ~5-10% single-thread overhead and up to 20% more memory (single Medium source); C extensions may silently re-enable the GIL; asyncio reworked in 3.14 so multiple event loops scale linearly across threads; FastAPI free-threading readiness still "in progress" per a March 2026 maintainer update. — [Quansight](https://labs.quansight.org/blog/scaling-asyncio-on-free-threaded-python); [Medium deep dive](https://medium.com/@mishra.writeto/python-3-14s-free-threaded-build-a-technical-deep-dive-23b2aabd3ee3); [cusy](https://cusy.io/en/blog/free-threaded-python-hit-or-miss.html); [oxykodit March 2026](https://oxykodit.substack.com/p/march-2026-update)
- Where Python bottlenecks in RAG: retrieval and LLM calls are I/O-bound and asyncio suffices; CPU-heavy steps (local embedding, reranking, chunking/parsing) are where the GIL matters, and NumPy-style libs already release the GIL. — [refontelearning](https://www.refontelearning.com/blog/free-threaded-python-backend-developers); [Quansight](https://labs.quansight.org/blog/scaling-asyncio-on-free-threaded-python)
- Hybrid pattern (Python for AI services + TypeScript gateway for streaming/API, Hono on Bun as common default) is the recurring 2026 recommendation; claims of 2-3x WebSocket throughput for Node over Python come without methodology. — [encore.dev](https://encore.dev/articles/typescript-backend-stack-2026-ai-agents); [heyuan110](https://www.heyuan110.com/posts/ai/2026-03-10-typescript-vs-python-ai-era)
- LiteLLM (AI gateway, ~61.7k stars) claims "8ms P95 latency at 1k RPS" with a Rust core and Python SDK; enterprise features under a commercial license. — [BerriAI/litellm](https://github.com/BerriAI/litellm)
- TechEmpower Round 23: only secondary coverage found (a Go framework reporting 658k RPS JSON serialization and placing 6th among Go frameworks; a Spring/Mongo config anomaly fixed from 583 to 14.2k RPS). Official per-framework rankings for Axum/Go/FastAPI/Litestar/Hono/Bun could not be retrieved. — [GoFrame](https://goframe.org/en/articles/techempower-web-benchmarks-r23); [TechEmpower blog](https://techempower.com/blog/2026/03/16/how-our-benchmarks-led-to-a-25x-mongodb-performance-improvement/)

#### (3) Orchestration frameworks
- Anthropic, "Building effective agents" (Dec 19, 2024; page now notes tooling has moved on): frameworks "can add abstraction layers that hide the underlying prompts and responses, which makes debugging harder"; "begin with LLM APIs directly, since many patterns take only a few lines of code"; single LLM calls with retrieval and in-context examples often suffice; the basic building block is an "augmented LLM" with retrieval, tools, memory, and MCP as the interface. — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- Octomind used LangChain in production 12+ months then removed it (2024) for simpler modular building blocks, reporting a simpler codebase and more productive team. — [octomind.dev](https://octomind.dev/blog/why-we-no-longer-use-langchain-for-building-our-ai-agents)
- "Orchestration framework trap" (Apr 2026): recurring 2024 postmortem theme was teams rewriting without LangChain and shipping faster; debugging hidden execution paths often requires LangSmith. — [tianpan.co](https://tianpan.co/blog/2026/04/19/orchestration-framework-trap-langchain-production)
- Abstraction layers add serialization/validation/callback overhead that compounds across multi-call agents and shows up in p95/p99. — [Towards Data Science](https://towardsdatascience.com/why-ai-engineers-are-moving-beyond-langchain-to-native-agent-architectures/)
- Pydantic AI (MIT, ~20.8k stars): typed end-to-end, model-agnostic, MCP in core, durable execution on Temporal/DBOS/Prefect/Restate/pgtask, OpenTelemetry-native; 1.0 cited as released April 2026 by a secondary source. — [pydantic/pydantic-ai](https://github.com/pydantic/pydantic-ai); [noqta](https://noqta.tn/en/blog/pydantic-ai-python-framework-production-agents-2026)
- LangGraph (MIT, ~43.6k stars): "low-level orchestration framework for ... long-running, stateful agents" with durable execution, human-in-the-loop, memory; names Klarna, Replit, Elastic as users; usable without LangChain. LangChain v1's create_agent is built on the LangGraph runtime. — [langchain-ai/langgraph](https://github.com/langchain-ai/langgraph); [insoftex](https://insoftex.com/ai-agent-frameworks-2026-langchain-vs-langgraph/)
- Consensus framing: Pydantic AI for mostly-linear typed agents, LangGraph when you need a checkpointed state machine; several sources say start with no framework. — [cut-the-saas](https://cut-the-saas.com/the-cut/best-ai-agent-frameworks); [ertas.ai](https://www.ertas.ai/compare/pydantic-ai-vs-langgraph)
- TypeScript options: Mastra (Apache-2.0, ~28.6k stars, agents+memory+workflows+evals, native MCP); Vercel AI SDK for chat UI hooks/streaming; Semantic Kernel for .NET/Azure shops; LlamaIndex/Haystack remain the document-first Python choices. — [futureagi](https://futureagi.com/blog/vercel-ai-sdk-alternatives-2026/); [gamut.so](https://www.gamut.so/blog/langchain-alternatives)

#### (4) Storage: Postgres single store vs specialized
- pgvector 0.8.7: HNSW + IVFFlat; `vector` indexable to 2,000 dims, `halfvec` to 4,000 dims (2 bytes/dim), `bit` and `sparsevec` types; iterative index scans (`hnsw.iterative_scan`, since 0.8.0) fix filtered-query recall collapse; HNSW builds much faster when the graph fits `maintenance_work_mem` (8GB shown as example). — [pgvector/pgvector](https://github.com/pgvector/pgvector)
- pgvectorscale (PostgreSQL license, ~3.1k stars): StreamingDiskANN index, SBQ compression, label-based filtering (smallint[] labels), Matryoshka dimension truncation; claims 28x lower p95 and 16x higher QPS vs Pinecone s1 at 99% recall on 50M Cohere 768-dim, 75% lower cost on EC2. — [timescale/pgvectorscale](https://github.com/timescale/pgvectorscale)
- TigerData (vendor, May 2025) pgvectorscale vs Qdrant on 50M Cohere 768-dim, 99% recall, r6id.4xlarge: 471.57 QPS vs 41.47 QPS; but Qdrant won p95 (36.73ms vs 60.42ms) and index build (3.3h vs 11.1h). — [TigerData](https://www.tigerdata.com/blog/pgvector-vs-qdrant); repeated by [Actian Q2 2026](https://www.actian.com/blog/developer/state-of-vector-databases-q2-2026/)
- Qdrant generally wins on filtered search performance (qualitative, March 2026). — [techsy](https://techsy.io/en/blog/qdrant-vs-chroma-vs-pgvector)
- Postgres HNSW memory: ~20-25 KB per 1536-dim vector with common settings; performance "falls off a cliff" once the graph exceeds RAM; builds can need 2-3x final index memory; a pgvector issue (#822) describes a partitioned build stalled >8h; mitigations: halfvec (halves index), binary quantization, DiskANN (pgvectorscale) degrades more gracefully; btree on tenant_id so planner picks selective path. — [ClickHouse engineering](https://clickhouse.com/resources/engineering/scale-vector-search-postgres); [particula](https://particula.tech/blog/pgvector-hnsw-tuning-millions-rows-production); [alex-jacobs "case against pgvector"](https://alex-jacobs.com/posts/the-case-against-pgvector)
- MariaDB's Feb 2026 10-database vector benchmark exists but used an old Qdrant 1.5.1, limiting its value. — [MariaDB](https://mariadb.org/big-vector-search-benchmark-10-databases-comparison/)
- ParadeDB (AGPL-3.0 community; enterprise commercial; ~9.4k stars): pg_search custom index with BM25, Top-K, highlighting, tokenizers, facets/aggregates, JOINs, vector + hybrid search; integrations for Drizzle/Django/SQLAlchemy/Rails/EF Core. Native Postgres `tsvector` ranking "is not BM25: no term-frequency saturation, no document-length normalization." Index updates happen in the same transaction (no ETL lag vs. an Elasticsearch sidecar). — [paradedb/paradedb](https://github.com/paradedb/paradedb); [softwareseni](https://www.softwareseni.com/replacing-elasticsearch-with-postgres-using-bm25-hybrid-search-and-rrf/)
- Vespa (Apache-2.0, Java/C++, ~7.1k stars) is the heavy-duty alternative (vectors, tensors, text, structured data at any scale) with a notably complex build/ops footprint; Onyx historically used it and newer templates show OpenSearch. — [vespa-engine/vespa](https://github.com/vespa-engine/vespa); [Railway Onyx template](https://railway.com/deploy/onyx-ai)
- Object storage: the MinIO GitHub repo states "THIS REPOSITORY IS NO LONGER MAINTAINED", was archived Apr 25, 2026, community edition is now source-only with no binary updates, and the replacement is commercial AIStor (Free or Enterprise editions). — [minio/minio](https://github.com/minio/minio)
- Job queues: Hatchet (MIT, ~8.2k stars) uses Postgres as the durability layer, SDKs in Python/TypeScript/Go/Ruby, DAG workflows, durable sleep/event waits, fair-scheduling concurrency keys, rate limits, OTel/Prometheus; load-tested to 10k tasks/s but "consumes more resources than a system built on Redis or RabbitMQ"; recommended when DAG work needs >100/s. — [hatchet-dev/hatchet](https://github.com/hatchet-dev/hatchet); [Hatchet vs Temporal](https://hatchet.run/versus/hatchet-vs-temporal)
- Temporal (MIT, ~23.9k stars) is the choice for millions of concurrent workflows / multi-region; supports Cassandra/MySQL/Postgres/SQLite persistence but is a multi-service cluster. — [temporalio/temporal](https://github.com/temporalio/temporal); [aicoolies Hatchet review](https://aicoolies.com/reviews/hatchet-review)
- pg-boss (MIT, ~4.1k stars): Node.js/Bun job queue on Postgres SKIP LOCKED with retries/backoff, DLQ, cron/RRULE, priority, dependency workflows, transactional enqueue via Drizzle/Knex/Kysely/Prisma, OTel; maintained by one person. — [timgit/pg-boss](https://github.com/timgit/pg-boss)
- Hatchet docs position BullMQ/Celery as the pick "for very high throughput without retention, or for a single library instead of a standalone service." — [Hatchet docs](https://docs.hatchet.run/llms-full.txt)

### Inferences
- For 50-200 engineers the API tier will never approach the RPS where Go/Rust/Bun separate from Python; the latency budget is dominated by LLM time-to-first-token (hundreds of ms to seconds) and ANN/rerank latency (tens of ms). Pick the backend language by who maintains it and where the ML libraries live, not by TechEmpower rank. Python (FastAPI or Litestar with msgspec) plus Pydantic AI, or TypeScript (Hono/Bun) plus Vercel AI SDK/Mastra, are both defensible; Rust/Go only pay off for the hot path (e.g., a LiteLLM-style gateway, which already exists).
- Keep CPU-bound stages (parsing with Docling, chunking, embedding, reranking) out of the request path and in workers (Hatchet) or dedicated servers (TEI, vLLM). That sidesteps the GIL entirely and makes the free-threading question moot for the API tier.
- A single Postgres (pgvector + pgvectorscale + ParadeDB or tsvector-with-RRF) is the right default at "tens of thousands of documents" (roughly 10^5-10^6 chunks): the index fits in RAM on a 32-64 GB node, transactions keep the wiki, ACLs, chunks, vectors and queue consistent, and permission filtering is a SQL WHERE clause rather than a cross-system sync. Reconsider a dedicated engine (Qdrant/Vespa/OpenSearch) only when the HNSW graph no longer fits RAM, filtered recall degrades despite iterative scans, or build times become operationally painful.
- ParadeDB's AGPL-3.0 is acceptable for an internal platform but worth a licensing review if the product is ever distributed; the fallback is Postgres FTS + RRF, accepting weaker BM25 ranking.
- MinIO's archival means a 2026 greenfield should not default to MinIO community binaries; use the cloud's S3, AIStor Free, or another S3-compatible store (Ceph RGW, SeaweedFS, Garage), with a thin S3 abstraction so the choice is swappable. (Alternatives list is inference; no source compared them.)
- Tiptap + Hocuspocus is the lowest-risk collaborative wiki editor: MIT on both, most recommended by neutral and competing vendors, and Hocuspocus's SQLite/Redis/S3 extensions cover single-node and HA. BlockNote is faster to a Notion-like UX but drags in MPL/GPL and less control. Lexical is viable for React-only teams that want a small core.
- Compose on one GPU host is the correct starting point for a small team; Kubernetes adds cost without benefit until there are multiple GPU nodes or SLO-driven canaries.
- Langfuse (MIT, richer prompt management) is the safer self-hosted observability pick for license reasons; Phoenix is lighter and more OpenTelemetry-pure but ELv2 and in corporate-acquisition flux. Either way, instrument via OpenTelemetry so the backend is swappable.
- Authentik is the pragmatic SSO pick for a small team (lightest, can proxy-protect legacy tools); Keycloak if the org already runs it or needs the deepest standards coverage; Zitadel if multi-tenant/API-first identity matters more than RAM.

## Key Question 2: Build on an existing open-source platform vs build a custom system on a few well-chosen components: tradeoffs and who has regretted each

### Takeaway
Turnkey platforms (Onyx, RAGFlow, Dify, AnythingLLM, Open WebUI, LibreChat) get a search-and-chat product live in days with connectors and permission sync, but each ships a fixed, heavy architecture (Onyx: Vespa/OpenSearch + Postgres + Redis + MinIO + Celery + two model servers) and none of them is a wiki or a compliance-checking engine. Documented regret runs the other way too: teams that built on LangChain-style frameworks report rewriting without them, while teams on Dify report "suboptimal recall" that they fixed by bolting on a separate retrieval engine. For a product whose core is a wiki plus structured compliance checks, the evidence favors building a thin custom system on Postgres + vLLM/TEI + Tiptap/Yjs, while borrowing Onyx's proven component layout and reusing Docling/TEI/vLLM/Hocuspocus rather than writing those layers.

### Inferences
- The requested product (ingestion + wiki + chat + compliance checking) does not match any turnkey platform's shape: Onyx/RAGFlow have no collaborative wiki editor and no rule/standard-driven compliance pipeline; adding those means forking a 11,000-commit codebase whose search tier (Vespa/OpenSearch) you do not otherwise want. ## Key Question 3: Which LLM and embedding deployment option gives the best latency and cost for ~50-200 users and tens of thousands of documents?

### Takeaway
For this scale the cheapest low-latency generation path is a hosted API with prompt caching (Claude Haiku 5.5 at $0.10/$0.50 per MTok under 100k-token prompts, Sonnet 5.5 at $2/$10, or open-weight gpt-oss-120b at ~$0.15/$0.60 on Groq/Together/Fireworks at ~500 tok/s), under a per-organization zero-data-retention agreement or via Bedrock/Vertex where the cloud provider is the data processor. Embeddings and rerankers should be self-hosted on TEI (Qwen3-Embedding-0.6B/4B and Qwen3-Reranker-0.6B/4B) because they are small, called on every query and on every ingested chunk, and keep document text in-house. Fully local generation (vLLM/SGLang with a Qwen3.x 30-35B-A3B MoE or gpt-oss-120b on one 80-96 GB GPU) costs roughly $900-$8,000/month in rented GPU or ~$31k per H100 purchased, is justified only by a hard data-residency requirement, and will be slower per token than Groq-class hosting.

A dedicated vector DB is unnecessary at this scale.

- Where a hosted frontier model is the right call: compliance checking against standards, where faithfulness and long-context reasoning matter and volume is low; use Sonnet 5.5 / Opus 5.5 with citations and 1M context (ZDR-eligible), not Fable/Mythos (Covered Models, 30-day retention, no ZDR unless authorized). - Privacy path ranking for a self-hostable platform: (1) fully local vLLM/TEI; (2) Bedrock/Vertex/Foundry inside your own cloud tenancy with regional endpoints (+10%) where the cloud provider is data processor; (3) first-party Claude API with a per-org ZDR agreement (CORS disabled; route via backend; no Batch API); (4) Groq/Together/Fireworks for open models (retention terms not verified here).
- Always self-host embeddings/rerankers regardless of generation choice: every chunk and every query passes through them, they are small (0.6B-4B), TEI supports them on modest GPUs or CPU, and it removes a per-call cost and a data-egress surface.

## Key Question 4: What are the biggest performance pitfalls reported in production RAG systems and how are they avoided?

### Takeaway
Production failures cluster in five places: (a) ingestion/chunking and parsing quality, (b) retrieval that is dense-only (misses exact identifiers) or lacks reranking, (c) vector-index operations (HNSW out of RAM, slow builds, filtered-recall collapse), (d) serving/concurrency mistakes (Ollama-style serialized inference, framework overhead in p99, no prompt caching), and (e) missing evaluation, stale indexes, permission leaks and no abstention. The fixes are well-documented: structure-aware chunking with contextual prefixes, hybrid BM25 + vector + reranker, index sizing/quantization and iterative scans, vLLM/SGLang with prefix caching, and CI evals plus ACL-filtered retrieval at the SQL layer.

### Cited Findings
- Vendor/practitioner claims that ~80% of RAG failures trace to ingestion/chunking and ~73% to retrieval rather than the LLM; recursive splitting at ~512 tokens scored best in one comparison; figures are unverified and directional. — [rocket.new](https://www.rocket.new/blog/production-rag-checklist-failures-tutorial-authors-never-cover); [aitraining2u](https://www.aitraining2u.com/blog/production-rag-patterns-2026.html)
- Dense-only search "misses exact terms like error codes and SKU strings"; the standard fix is hybrid BM25 + embeddings, then rerank; respect document structure (headers, paragraphs, tables need different strategies); HyDE and multi-query help recall; "confident wrong answers are worse than admitting ignorance." — [dev.to RAG 2026](https://dev.to/ai_builder/rag-in-production-in-2026-beyond-naive-chunk-and-embed-3803); [codingshuttle](https://www.codingshuttle.com/blogs/building-production-ready-rag-hybrid-search-reranking-and-conversational-memory); [xyz.dev](https://xyz.dev/blog/rag-production)
- Anthropic's measured fix for context loss in chunks: contextual embeddings + contextual BM25 + reranking reduce top-20 retrieval failures by 67%; retrieve 150, rerank to 20; top-20 beat top-5/10. — [Anthropic](https://www.anthropic.com/news/contextual-retrieval)
- Silent production failures: stale indexes, permission leaks across tenants, "confident" answers with weak grounding, evaluations that never catch regressions; build abstention behavior. — [Sessionize abstract](https://sessionize.com/s/sidharth-gopakumar/rag-in-production-what-breaks-after-the-happy-path/189253)
- Teams "underinvest in evals and overinvest in swapping vector databases"; other breakpoints: cost scaling faster than planned, governance. — [jobsbyculture](https://jobsbyculture.com/blog/production-rag-guide-2026); [Towards Data Science six lessons](https://towardsdatascience.com/six-lessons-learned-building-rag-systems-in-production/)
- Vector index pitfalls: HNSW latency "falls off a cliff" when the graph exceeds RAM; builds need 2-3x memory; a partitioned pgvector build stalled at 29.2% for 8+ hours (issue #822); filtered queries collapsed in pgvector <=0.7.4 (completeness as low as 1% on one workload) and 0.8.0 iterative scans fixed it; mitigations: `hnsw.iterative_scan`, btree on tenant_id, halfvec, binary quantization, DiskANN. — [ClickHouse](https://clickhouse.com/resources/engineering/scale-vector-search-postgres); [particula](https://particula.tech/blog/pgvector-hnsw-tuning-millions-rows-production); [bigdataboutique](https://bigdataboutique.com/blog/pgvector-in-production); [pgvector README](https://github.com/pgvector/pgvector)
- Serving pitfalls: Ollama's default one-request-at-a-time cap left throughput flat at 41 tok/s vs vLLM's 793 tok/s on the same A100. — [Red Hat](https://developers.redhat.com/articles/2025/08/08/ollama-vs-vllm-deep-dive-performance-benchmarking)
- Framework overhead compounds across multi-call agents and shows in p95/p99; hidden execution paths make failures hard to trace. — [Towards Data Science](https://towardsdatascience.com/why-ai-engineers-are-moving-beyond-langchain-to-native-agent-architectures/); [tianpan.co](https://tianpan.co/blog/2026/04/19/orchestration-framework-trap-langchain-production)
- Agentic RAG cost trap: "a single complex agentic task might make five MCP calls, easily tripling your per-request token spend compared to a single RAG-enhanced completion"; a retrieve-then-generate pipeline runs 500ms-2s per query; MCP tool calls need retries with backoff, circuit breakers and timeout budgets. — [tkmxai](https://tkmxai.it.com/rag-vs-mcp-in-2026-8)
- Platform-level pitfalls: RAGFlow needs `vm.max_map_count=262144` and 16 GB minimum; Onyx needs ~2 GB RAM per GB of source docs for small corpora. — [Railway RAGFlow](https://railway.com/deploy/ragflow-vs-dify--deploy-ragflow-vs-dify-rag-engine); [Onyx resourcing](https://docs.onyx.app/deployment/getting_started/resourcing.md)
- Pricing/tokenizer pitfalls: Claude 4.7+ tokenizer yields ~30% more tokens; Haiku 5.5 jumps 5x in price above 100k-token prompts and the whole request is billed at the higher tier even with cache hits; GPT-5.5 doubles input price above 272k tokens. — [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing); [morphllm OpenAI](https://morphllm.com/openai-api-pricing)
- Supply-chain pitfall: MinIO community repo archived Apr 25, 2026 with no further binary updates. — [minio/minio](https://github.com/minio/minio)
- Document parsing pitfall: general VLMs (GPT-4o-mini 55.56) beat dedicated parsers (Marker 46.44, MinerU 46.08) on READoc structured extraction, so parser choice should be validated on your own PDFs. — [READoc](https://arxiv.org/pdf/2409.05137)

### Inferences
- The highest-leverage mitigations for this platform, in order: (1) structure-aware chunking via Docling + Anthropic-style contextual prefixes generated once at ingest with Haiku 5.5 or a local small model; (2) hybrid retrieval in one SQL query (pgvector + BM25 via ParadeDB or tsvector + RRF) followed by Qwen3-Reranker-0.6B/4B on TEI, retrieving ~150 and passing ~20 chunks; (3) ACL enforcement as a WHERE clause on the chunk table (tenant/space/user-group columns with btree indexes) rather than post-filtering in application code, which also avoids the filtered-recall cliff; (4) prompt caching of system prompt + stable retrieved context; (5) DeepEval/Ragas retrieval and faithfulness metrics run in CI on a golden set from day one, with Langfuse/Phoenix traces feeding the dataset; (6) vLLM/SGLang (never Ollama) if anything is self-hosted; (7) a freshness pipeline (Hatchet jobs triggered by wiki edits and connector webhooks) so the index never lags the wiki, with the index update in the same transaction where possible.
- Keep Haiku 5.5 prompts under 100k tokens (the 20-chunk pattern is ~16-20k) to stay in the $0.10/$0.50 tier; for compliance checks that need whole-standard context, use Sonnet 5.5's flat-rate 1M context instead of Haiku's over-100k tier.
- Because agentic loops multiply token spend 3-5x, reserve agentic multi-hop retrieval for the compliance-check workflow and "deep research" mode, and keep the default chat path as a single retrieve-rerank-generate call.
