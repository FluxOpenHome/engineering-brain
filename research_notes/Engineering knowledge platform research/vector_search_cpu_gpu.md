# Retrieval architecture for an engineering document knowledge base: vector DB need/choice, CPU vs GPU per stage, embedding/reranker SOTA, hybrid & GraphRAG evidence, hardware sizing (state as of October 2026)

Research method note: many primary sites (arxiv.org, qdrant.tech, timescale.com, huggingface.co, runpod.io) were unreachable from the research sandbox (proxy 403), so most figures below come from search-engine extracts of those pages plus GitHub READMEs that were fetched directly. Where a figure is vendor-published or second-hand this is flagged. Scale assumption used throughout: 10k-100k engineering PDFs at ~20-50 chunks/doc => roughly 0.5M-5M chunks (vectors); 1M-10M vectors is the relevant ANN regime.

## Q1. Is a dedicated vector database required at tens-of-thousands of documents, and which self-hosted engine is the best default?

### Takeaway
No dedicated vector DB is *required* at 0.5M-5M vectors: Postgres + pgvector (ideally with pgvectorscale) and embedded engines (LanceDB, SQLite-based) all serve 1M-10M vectors at single-digit-to-tens-of-ms p95 on one node. The practical decision is about filtered search quality, hybrid (BM25+dense) support, multi-vector (ColBERT/ColPali) support, and ops burden. For a self-hosted, fast, efficient default that also wants metadata filtering, native BM25/sparse hybrid, multi-vector and quantization, Qdrant (Apache-2.0, single Rust binary) is the most frequently recommended; pgvector/pgvectorscale is the right default if Postgres is already the system of record and you want one database for metadata + vectors + full-text search.

### Cited Findings
- Scale/memory: Qdrant's own benchmark notes that the largest test set, dbpedia-openai-1M-1536-angular (1M vectors x 1536-d), "needs roughly 8.6 GB of RAM including vectors and index"; the benchmark ran every engine under a 25 GB memory cap — [Qdrant single-node benchmark](https://qdrant.tech/benchmarks/single-node-speed-benchmark/)
- Qdrant's own (vendor) summary: Qdrant posted "the highest throughput and lowest latencies in nearly all scenarios", Elasticsearch "search speed improved, but indexing is very slow ... 10x slower when storing 10M+ vectors of 96 dimensions (32 minutes vs 5.5 hours)", Milvus "indexing is fastest, but trails on throughput and latency with higher-dimension embeddings", Redis "good throughput, mostly at lower precision" — [Qdrant benchmarks](https://qdrant.tech/benchmarks/)
- Independent-ish 1M-vector comparison (blog): Qdrant HNSW+scalar quantization 6.8 ms p95 and 1,240 req/s, ahead of Milvus 2.4 and pgvector 0.7 — [DEV Community: Vector databases for production RAG 2026](https://dev.to/locionic/vector-databases-for-production-rag-2026-pinecone-vs-qdrant-vs-milvus-vs-pgvector-4fim)
- A matched-recall test found Milvus and Weaviate near 3 ms p95, Qdrant 5.3 ms, pgvector 6.3 ms; Milvus reached a queryable index fastest (~4.8 min) — [Salt Techno vector DB benchmark 2026](https://www.salttechno.ai/datasets/vector-database-performance-benchmark-2026/) (methodology unclear)
- AIMultiple open-source benchmark: mixed read/write QPS Milvus 930 / pgvector 536 / Qdrant 455; read-only QPS pgvector 885 / Qdrant 723; Qdrant highest recall (0.99) — [AIMultiple](https://aimultiple.com/open-source-vector-databases)
- pgvectorscale (Timescale/TigerData, PostgreSQL license) on 50M Cohere 768-d vectors at 99% recall: "28x lower p95 latency, 16x higher query throughput" and ~75% lower cost than Pinecone s1; StreamingDiskANN index, SBQ compression (2 bits/dim <900-d, 1 bit/dim otherwise); label filtering follows Filtered-DiskANN, arbitrary WHERE clauses are post-filters; results use relaxed ordering — [pgvectorscale GitHub README](https://github.com/timescale/pgvectorscale)
- TigerData vs Qdrant at 50M vectors / 99% recall: "an order of magnitude more throughput than Qdrant" while keeping latency <100 ms, but concedes "Qdrant does achieve better tail latencies for high recall vector search" — [TigerData pgvector vs Qdrant](https://www.tigerdata.com/blog/pgvector-vs-qdrant); a third-party write-up of the same setup quotes 471 QPS (pgvectorscale, p95 ~28 ms) vs 41 QPS (Qdrant) — [Towards AI (Medium)](https://pub.towardsai.net/i-benchmarked-pgvector-vs-qdrant-vs-pinecone-on-50m-vectors-postgres-crushed-the-dedicated-dbs-by-20aa6dcdf132); the same write-up notes the gap narrows at 1M vectors (Qdrant 626 QPS at 99.5% recall) — numbers are unverified and vendor-adjacent
- Plain pgvector practical ceiling: one guide puts pgvector's practical ceiling at ~10M vectors while Milvus/Qdrant list billions — [Firecrawl: best vector databases](https://www.firecrawl.dev/blog/best-vector-databases)
- Filtered search: plain pgvector HNSW post-filters, so with default `hnsw.ef_search=40` and a 10%-selective filter "only 4 rows will match on average"; pgvector 0.8.0 added iterative index scans bounded by `hnsw.max_scan_tuples` (`strict_order` vs `relaxed_order`), and raising max_scan_tuples "can significantly increase latency" — [ClickHouse: scaling vector search in Postgres](https://clickhouse.com/resources/engineering/scale-vector-search-postgres), [bigdataboutique: pgvector in production](https://bigdataboutique.com/blog/pgvector-in-production)
- Qdrant applies filters *during* HNSW traversal ("filterable HNSW", extra graph links respecting payload indexes). A third-party (pgContext) test on 100k vectors at 10% selectivity: filtered recall@10 0.4225 for pgvector (default settings, not iterative scans) vs 1.0000 for Qdrant; Qdrant built the graph ~20x faster than pgvector — [pgContext pgvector benchmark](https://pgxn.org/dist/pgContext/docs/benchmarks/pgvector.html)
- Hybrid in Qdrant: dense + sparse (BM25 via FastEmbed `Qdrant/bm25` with IDF modifier) prefetch and native RRF fusion in one `query_points` call; adding a sparse vector to an existing dense-only collection requires a new collection + full reindex — [Qdrant hybrid search docs](https://qdrant.tech/documentation/search-tuning/hybrid-search/)
- Multi-tenancy in Qdrant: docs say "in most cases, you should only use a single collection with payload-based partitioning"; Qdrant Cloud default limit 1,000 collections; user-defined sharding for big tenants; Qdrant 1.16+ adds tiered multitenancy (shared fallback shard + dedicated shards) — [Qdrant multitenant docs](https://qdrant.tech/documentation/production-operations/multitenant-search/), [OneUptime: collection per tenant vs payload partitioning](https://oneuptime.com/blog/post/2026-08-28-qdrant-one-collection-per-tenant-or-payload-partitioning/markdown)
- Memory footprint rules of thumb: Qdrant docs give ~3 GB float32 for 1M x 768-d, binary quantization = 32x compression; HNSW graph stores 4-byte connections per link; a community rule of thumb is HNSW M=16 ≈ 1.3x raw data size — [Qdrant large-scale search tutorial](https://qdrant.tech/documentation/tutorials-operations/large-scale-search/), [Qdrant quantization (mirror)](https://www.mintlify.com/qdrant/qdrant/advanced/quantization), [Zilliz FAQ on HNSW overhead](https://zilliz.com/ai-faq/how-much-memory-overhead-is-typically-introduced-by-indexes-like-hnsw-or-ivf-for-a-given-number-of-vectors-and-how-can-this-overhead-be-managed-or-configured)
- Turbopuffer is object-storage based: "much cheaper for large corpora, at the cost of some latency"; it is a hosted service (not self-hostable) — [DEV: vector DB comparison 2026](https://dev.to/alexcloudstar/vector-database-comparison-2026-pgvector-pinecone-turbopuffer-and-qdrant-55ak)
- Qdrant described as "the default pick for people who want serious filtering and hybrid search without paying Pinecone prices", with native multi-vector retrieval as its 2026 strength; LanceDB "still has fans" but did not get prime billing — [noqta: vector database comparison 2026](https://noqta.tn/en/blog/vector-database-comparison-2026-pgvector-pinecone-qdrant-weaviate)
- Licenses: Elasticsearch added AGPLv3 (2024) for source, but downloadable builds remain Elastic License 2.0 / SSPL per one source; OpenSearch Apache-2.0; Weaviate BSD-3; Milvus and Chroma Apache-2.0 (older source, 2023-era) — [sdxcentral Elastic AGPL press release](https://www.sdxcentral.com/press-releases/elastic-announces-open-source-license-for-elasticsearch-and-kibana-source-code/), [d-central self-hosted vector DBs](https://d-central.tech/self-hosted-vector-databases/), [KDnuggets honest comparison](https://kdnuggets.com/an-honest-comparison-of-open-source-vector-databases); Qwen3/Qdrant licensing: Qdrant Apache-2.0 (see Qdrant GitHub); pgvectorscale PostgreSQL license — [pgvectorscale GitHub](https://github.com/timescale/pgvectorscale)
- Kubernetes/ops view: pgvector is easiest to start (extension on an existing Postgres), weaker at very large scale — [lucaberton Qdrant vs Milvus vs pgvector on K8s](https://lucaberton.com/blog/vector-database-kubernetes-qdrant-milvus-pgvector-2026/), [computingforgeeks best self-hosted vector DB 2026](https://computingforgeeks.com/qdrant-weaviate-milvus-pgvector/)
- Multi-vector (ColPali/ColQwen) is supported natively in Qdrant with pooling to cut vectors per page (1,030 -> 38 with row pooling) — [Qdrant PDF retrieval at scale tutorial](https://qdrant.tech/documentation/tutorials-search-engineering/pdf-retrieval-at-scale/), [Qdrant ColPali optimization blog](https://qdrant.tech/blog/colpali-qdrant-optimization/)

### Inferences
- At the target scale (0.5M-5M chunks), memory for float32 1024-d vectors is ~2-20 GB plus ~30% HNSW overhead; with scalar quantization (4x) or binary quantization (32x) it fits comfortably in 16-64 GB RAM on a single node. Memory, not QPS, is the only scaling dimension that matters here, and it is small.
- The sub-10 ms p95 single-node latency of Qdrant/Milvus/Weaviate/pgvector at 1M vectors means ANN search is never the latency bottleneck of a RAG pipeline (LLM generation is, by 2-3 orders of magnitude).
- Decision rule: (a) Postgres already in place + modest filtering + want SQL joins => pgvector 0.8+ with pgvectorscale and tsvector hybrid; (b) heavy metadata filtering (doc type, revision, project, tenant), BM25+dense hybrid, binary quantization, multi-vector ColPali => Qdrant; (c) single-process/desktop deployment => LanceDB or sqlite-vec (embedded, no server); (d) Elasticsearch/OpenSearch only if you already run it for logs/text search (OpenSearch Apache-2.0 avoids the Elastic license question); (e) Milvus/Weaviate/Vespa are justified at >100M vectors or where their specific features (Vespa's tensor ranking, Milvus GPU indexes) are needed.
- "Do we need a vector DB at all?" The honest answer: you need *an ANN index with filtering and hybrid search*; whether it lives inside Postgres or in a dedicated process is an ops choice. For a 1-3 person team wanting minimum moving parts, one Postgres instance is the least ops; for best filtered-recall and hybrid out of the box, Qdrant is one extra container.

### Gaps
- No vendor-neutral 2025-2026 benchmark that runs pgvector 0.8 with tuned iterative scans head-to-head against Qdrant filterable HNSW at matched recall was found.
- Could not fetch the current Qdrant benchmark page (2024-2025 rerun) to extract per-dataset QPS/p95 at 1M-10M; only the 2022-era summary and third-party quotes were reachable.
- No quantitative latency figures for LanceDB, Vespa or Turbopuffer at 1-10M vectors were found; sqlite-vec / embedded SQLite options returned no benchmark data.
- Chroma 2026 license/performance status not confirmed.

## Q2. CPU vs GPU for each stage (ingest embedding, query embedding, ANN search, reranking, LLM generation) with throughput numbers

### Takeaway
GPU pays off decisively for (1) bulk ingest embedding (roughly 10-100x faster than CPU for 300M-600M-param models), (2) PDF parsing/OCR/layout (≈7x at median page), (3) cross-encoder reranking (~30x per pair), and (4) LLM generation (CPU-only 70B is 3-11 tok/s vs 25-50 tok/s single-stream and 1,400-1,850 tok/s aggregate on one H100). ANN search and single-query embedding are fine on CPU: ANN at 1-10M vectors is single-digit ms on CPU HNSW, and only index *build* benefits from GPU (≈11-14x at 10M vectors).

### Cited Findings
**Embedding generation (ingest and query)**
- TEI on datacenter GPUs, bge-m3 at 512-token passages: ~1,345 texts/s on H200, ~277 on L40S, ~190 on RTX A5000; MiniLM-L6-v2 ~650,000 tokens/s on RTX 2000 Ada — [RunPod: best GPU for embedding workloads](https://www.runpod.io/blog/gpu-embedding-workloads-benchmark) (no CPU baseline in that article)
- Vendor FAQ (marketing-grade): RTX 4090 ~8,500 docs/s with BGE-large-en-v1.5 (batch 256, 512 tokens, FP16) vs an unnamed 8-core CPU at 50-100 docs/s — [io.net FAQ](https://io.net/p/faq-how-do-i-run-embedding-models-at-scale-for-rag-pipelines)
- CPU small models: MiniLM-class 5-14k sentences/s on CPU vs 1-2k for larger models (short sentences, unspecified CPU) — [Introl: embedding infrastructure at scale](https://introl.com/blog/embedding-infrastructure-scale-vector-generation-production-guide-2025)
- CPU/ONNX: bge-m3 ONNX fp32 export was only ~1.27x faster than PyTorch on x86 for long documents (857 ms vs 1,091 ms per embed); dynamic int8 degraded quality (dense cosine 0.985 vs fp32) so the author did not ship it — [a-ivanovitch/bge-m3-onnx](https://huggingface.co/a-ivanovitch/bge-m3-onnx)
- Compact multilingual encoder on CPU: 364 docs/s on Apple Silicon (MPS) and 297 docs/s CPU-only via OpenVINO for a ~100M-class model — [Bekko Embedding paper](https://arxiv.org/pdf/2607.25180)
- Snowflake Arctic Inference + vLLM: 16x (50-token) and 4.2x (512-token) higher embedding throughput than plain vLLM; 2.4x TEI on short sequences, parity on long; headline 1.4M-1.6M tokens/s per GPU for snowflake-arctic-embed-m-v1.5 (A10G-class production GPUs) — [Snowflake engineering blog](https://www.snowflake.com/en/engineering-blog/embedding-inference-arctic-16x-faster/), [Arctic Inference paper](https://arxiv.org/pdf/2507.11830)
- TEI supports CPU (ONNX/MKL), Metal, CUDA (Turing..Blackwell incl. RTX 50x0 and DGX Spark), ROCm; serves BERT/XLM-R (bge-m3), Qwen3, Gemma3, ModernBERT embeddings and bge/gte rerankers; Apache-2.0; current image tag 1.9 — [TEI GitHub](https://github.com/huggingface/text-embeddings-inference)

**PDF parsing (ingest pre-step, often the real bottleneck)**
- Docling median page time: 0.79 s on x86 CPU (~1.3 pages/s), 0.32 s on M3 Max (~3 pages/s), 114 ms on NVIDIA L4 (~9 pages/s); OCR is 50-60% of runtime; GPU speedup 8x OCR, 14x layout, 4.3x table structure — [Docling paper](https://arxiv.org/pdf/2501.17887)
- Third-party (FibrumPDF maintainer) Ryzen 7 benchmark: Docling 0.62 pages/s with table TEDS 0.821 — [fibrum-pdf PyPI](https://pypi.org/project/fibrum-pdf)

**ANN search and index build**
- Query latency at 1M vectors on CPU: 3-7 ms p95 across Milvus/Weaviate/Qdrant/pgvector (see Q1 sources) — [Salt Techno](https://www.salttechno.ai/datasets/vector-database-performance-benchmark-2026/), [DEV locionic](https://dev.to/locionic/vector-databases-for-production-rag-2026-pinecone-vs-qdrant-vs-milvus-vs-pgvector-4fim)
- GPU index build: OpenSearch 10M x 768-d HNSW (m=16, ef_construction=256) build 8.5 h on 3x r6g.4xlarge CPU vs 36.8 min on 3x g5.2xlarge A10G = 14x — [OpenSearch GPU vector search blog](https://opensearch.org/?p=4066); Milvus 1M x 768-d: 454 s CPU vs 42 s A10G (~11x) — [Zilliz: Milvus on GPU with cuVS](https://zilliz.com/blog/milvus-on-gpu-with-nvidia-rapids-cuvs); CAGRA up to 12.3x faster build on Deep100M — [NVIDIA cuVS/FAISS blog](https://developer.nvidia.com/blog/enhancing-gpu-accelerated-vector-search-in-faiss-with-nvidia-cuvs)

- bge-reranker-v2-m3 on CPU scored 3 documents in ~350 ms; "adding a reranker means 50-400 ms extra latency per query" — [bswen: best reranker models 2026](https://docs.bswen.com/blog/2026-02-25-best-reranker-models/)

### Inferences
- Ingest sizing example (100k docs x 30 pages x ~40 chunks of ~400 tokens = ~4M chunks, ~1.6B tokens): bge-m3-class on one L40S/4090-class GPU at ~250-400 texts/s => ~3-5 h; on a 16-core CPU at an optimistic 20-50 texts/s for a 560M-param model at 512 tokens => 1-2 days. Smaller models (MiniLM/bge-small/jina-v5-nano at ~0.1-0.2B) narrow the gap to a few hours on CPU. PDF parsing with layout+table models is often *slower* than embedding: Docling at 1.3 pages/s CPU => 3M pages ≈ 26 CPU-days single-process vs ~4 GPU-days on an L4 (parallelize across cores/processes accordingly).
- Query path on CPU is fine: query embedding of one 30-token query with a 0.3-0.6B model is ~20-80 ms on CPU; ANN 3-10 ms; the reranker is the only CPU-sensitive query component (50 x 512-token pairs ~2 s on CPU vs <0.1 s on GPU). If you want <500 ms end-to-end retrieval with reranking at 10+ concurrent users, put the reranker on a GPU (or use a small reranker on top-10 only).
- LLM generation is where GPU is non-negotiable for interactive use: CPU-only 70B at 3-11 tok/s is below reading speed and collapses under concurrency; one 24-32 GB consumer GPU serves an 8B-14B class model at 100-200 tok/s single-stream and ~2,500 tok/s aggregate, enough for ~20-50 concurrent chat users; 70B at FP8 needs 80 GB (one H100/H200) and gives ~1,500-1,850 tok/s aggregate.
- GPU for ANN *search* is unnecessary at <10M vectors; GPU index build (cuVS/CAGRA) only matters for very frequent full re-indexes.

### Gaps
- No like-for-like TEI benchmark of the same model on CPU and GPU was found; CPU embedding throughput for bge-m3 / Qwen3-Embedding-0.6B at realistic 512-token chunks is only estimable from indirect data.
- No first-party 2026 llama.cpp numbers for RTX 5090 / Blackwell datacenter GPUs or for 70B on 12-channel EPYC Turin were found; the May-2024 GitHub table is the most controlled dataset located.
- No measured bge-reranker-v2-m3 CPU-vs-GPU figure at 50 passages.

## Q3. State-of-the-art, practical embedding models and rerankers for technical/engineering text in 2026 (multilingual, long-context, tables/figures)

### Takeaway
Open-weight leaders are the Qwen3-Embedding family (0.6B/4B/8B, Apache-2.0, 32K context, 100+ languages, Matryoshka dims) with Qwen3-Reranker as companion; jina-embeddings-v5-text (677M/239M, 32K/8K ctx, distilled from Qwen3-Embedding-4B) is the compact 2026 option; BGE-M3 (dense+sparse+multi-vector in one model) remains the pragmatic hybrid workhorse. Hosted leaders are Voyage-4 (32K ctx, $0.02-0.12/M tokens, tops RTEB), Gemini Embedding, OpenAI text-embedding-3-large ($0.13/M). For rerankers, jina-reranker-v3 scores highest on BEIR (61.7-61.9 nDCG@10) but is CC-BY-NC; Qwen3-Reranker-4B/8B (59.9/61.8) and bge-reranker-v2-m3 (~56) are the commercial-friendly self-hosted choices; Cohere Rerank 4 is the API leader. For page images with tables/figures, ColQwen2.5/ColPali-style late interaction scores ~89 nDCG@5 on ViDoRe v1 but tables are a relative weak spot and storage is 60-500x a single vector unless pooled.

## Q4. Do hybrid search (BM25 + dense) and GraphRAG/knowledge graphs materially improve accuracy for technical documents?

### Takeaway
Hybrid lexical+dense fusion is the single most evidence-backed improvement: on text-and-table financial filings, RRF hybrid raised Recall@5 to 0.695 vs 0.644 BM25 and 0.587 dense, and adding a neural reranker reached 0.816, with the largest gains on table-heavy questions; BM25 alone beat SOTA dense retrieval on those documents. GraphRAG helps on multi-hop/global synthesis questions but not single-hop lookups in the neutral academic comparison; full GraphRAG indexing is ~1,000x the indexing cost of vector RAG (LazyGraphRAG brings it back to parity), and the large 2026 accuracy gaps (+16 pts, +80%) come from vendor-published benchmarks.

### Cited Findings
**Hybrid (BM25 + dense) and reranking**
- Text-and-table financial documents benchmark (Apr 2026): Recall@5 hybrid RRF 0.695 vs BM25 0.644 vs dense 0.587; two-stage pipeline with neural reranking 0.816; gain largest on table-heavy questions (~+8 pts Recall@5 over BM25 on TAT-DQA); "BM25 outperforms state-of-the-art dense retrieval on financial documents"; prior-work citation of 15-30% recall improvement from hybrid — [From BM25 to Corrective RAG (arXiv 2604.01733)](https://arxiv.org/html/2604.01733v1)
- TREC ToT 2025: fusing LLM, BM25 and BGE-M3 dense beat the best single method on every dev set, relative recall@1000 gains 4-11% — [DS@GT at TREC TOT 2025](https://arxiv.org/pdf/2601.15518)
- Counter-evidence: on WANDS e-commerce (Mar 2025) BM25 and dense were statistically tied; in highly technical / matching-sensitive domains, heavier BM25 weighting often stays optimal — [Emergent Mind: Hybrid BM25 retrieval](https://www.emergentmind.com/topics/hybrid-bm25-retrieval), [Hybrid Dense-Sparse Retrieval for High-Recall IR](https://www.researchgate.net/publication/399428523_Hybrid_Dense-Sparse_Retrieval_for_High-Recall_Information_Retrieval)
- Practitioner guides claim adding BM25 + cross-encoder reranker yields 15-25% accuracy improvement without graph infrastructure (vendor blog) — [VentureBeat: when GraphRAG beats vector RAG](https://venturebeat.com/orchestration/stop-graphing-everything-when-graphrag-actually-beats-vector-rag), [Towards Data Science: hybrid search and re-ranking](https://towardsdatascience.com/hybrid-search-and-re-ranking-in-production-rag/)
- Rerankers in production: adding one costs 50-400 ms per query (see Q2) — [bswen](https://docs.bswen.com/blog/2026-02-25-best-reranker-models/)

**Chunking of technical documents with tables/units**
- Structure-aware chunking scored best on generation metrics while semantic chunking best kept tables intact (65 structured institutional documents, 4 strategies) — [IJACSA: Effective chunking for RAG](https://thesai.org/Downloads/Volume17No8/Paper_54-Effective_Chunking_for_Retrieval_Augmented_Generation.pdf)
- Structure-aware chunking for complex multi-row/column tables reached answer accuracy 0.73 vs baselines (RAGAS) — [Structure-Aware Chunking for Complex Tables](https://shdl.mmu.edu.my/15426/)
- NVIDIA's RAG blueprint keeps tables and charts as complete units rather than splitting them — [NVIDIA developer blog](https://developer.nvidia.com/blog/?p=102394)
- Fixed-token cuts can separate a claim from its unit or scope (commentary) — [ZimaSpace: chunk boundaries](https://shop.zimaspace.com/blogs/tech-ai-hub/rag-chunk-boundaries-change-home-ai-search-evidence); "Seven Failure Points" calls for systematic chunking comparison and flags tables/formulas as understudied — [Seven Failure Points When Engineering a RAG System](https://arxiv.org/pdf/2401.05856)

**GraphRAG / knowledge graphs**
- Neutral academic comparison (MSU/Meta, 2025): under one protocol, plain RAG edged ahead on single-hop factual lookup; graph-guided retrieval ahead on multi-hop reasoning; "no single winner" — [RAG vs GraphRAG: a systematic evaluation](https://arxiv.org/pdf/2502.11371)
- Vendor benchmark (FalkorDB, Aug 2026) on GraphRAG-Bench: 71.48 overall accuracy vs 55.39 for vector RAG with reranking (+16.09 pts, ~29% relative); competitor numbers not re-run by FalkorDB — [FalkorDB GraphRAG accuracy benchmark](https://docs.falkordb.com/graphrag/graphrag-accuracy-benchmark)
- Neo4j-cited 2026 NICD study: GraphRAG answered 65.3% of 510 complex questions vs 28.9% vector-only (~80% higher truthfulness); original not verified — [Neo4j: Vector RAG vs GraphRAG](https://neo4j.com/blog/agentic-ai/vector-rag-vs-graphrag/)
- Cost: LazyGraphRAG indexing cost matches vector RAG and is ~0.1% of full GraphRAG's; at 500 relevance tests it beat all conditions on local and global queries at 4% of GraphRAG C2 query cost; authors warn "not every use case should be lazy" — [Microsoft Research LazyGraphRAG](https://www.microsoft.com/en-us/research/blog/lazygraphrag/); secondary: graph extraction ~75% of GraphRAG indexing cost, query latency +2-8 s for on-demand summaries — [Particula LazyGraphRAG](https://particula.tech/blog/lazygraphrag-700x-cheaper-graphrag-knowledge-graphs), [TianPan GraphRAG in production](https://tianpan.co/blog/2026-04-09-graphrag-production-when-vector-search-hits-ceiling)
- Hallucination benchmark on fact-dense queries compares Graph-RAG and standard RAG — [MachineLearningMastery](https://machinelearningmastery.com/evaluating-graph-rag-vs-standard-rag-a-hallucination-benchmark-on-fact-dense-queries/)

### Inferences
- For engineering specs (numbered requirements, part numbers, unit-bearing values, standard clause IDs like "IEC 61508-2 §7.4.4"), the lexical channel is essential: exact tokens (clause numbers, part codes, unit strings) are exactly what dense models blur and BM25 nails; the financial text+table result (BM25 > dense; hybrid+rerank +23 pts Recall@5 over dense) is the closest available proxy.
- Priority order by measured impact and cost: (1) hybrid BM25+dense with RRF, (2) cross-encoder reranking of top-30/50, (3) structure-aware chunking that keeps tables, headers and requirement IDs whole and prepends section breadcrumbs, (4) only then consider graph/relationship retrieval for cross-document traceability questions (e.g., "which drawings and test reports reference requirement REQ-123") - and prefer a lightweight explicit metadata/citation graph (document->references->clause) stored as Postgres/Qdrant payload over LLM-extracted entity graphs, whose indexing cost is ~1,000x.
- GraphRAG's documented wins are on multi-hop/global "summarize themes" queries; a typical engineer's query ("what is the max operating temperature of part X per spec Y rev C") is single-hop, where plain hybrid RAG is as good or better.

### Gaps
- No controlled study of hybrid vs dense on engineering standards/specifications specifically; evidence transfers from financial filings and multilingual scientific retrieval.
- GraphRAG-Bench numbers come from a vendor; Microsoft's original GraphRAG paper and the 2502.11371 paper could not be fetched directly for exact per-task scores.
- No study quantifying unit-normalization or number-aware retrieval improvements was found.

## Q5. Hardware sizing for three tiers (workstation; small on-prem server with one GPU; cloud) at 10k-100k documents and 10-200 concurrent users, plus local vs API cost/latency

### Takeaway
Vectors are small (0.5M-5M chunks ≈ 2-20 GB float32, 0.5-5 GB with scalar quantization), so storage/ANN fit on any tier; the GPU budget is driven by LLM generation and reranking. Tier 1 (workstation, RTX 5090 32 GB or 4090 24 GB, 64-128 GB RAM): 8B-14B LLM at 100-200 tok/s, ~10 concurrent users, embedding + reranking on the same GPU. Tier 2 (one 48-96 GB GPU such as L40S/RTX 6000 Pro, or one H100/H200 80 GB for 70B FP8): 30-70B models at ~1,500-1,850 aggregate tok/s, 50-100 concurrent users. Tier 3 (cloud): same single-GPU sizing per ~50-100 users, or offload generation to Claude/OpenAI APIs (Haiku-class at $0.10/$0.50 per MTok makes API generation cheaper than owning a GPU below ~a few million tokens/day) while keeping embeddings/ANN local.

### Cited Findings
- Memory: 1M x 768-d float32 ≈ 3 GB; 1M x 1536-d dbpedia incl. HNSW ≈ 8.6 GB; binary quantization 32x smaller — [Qdrant quantization](https://www.mintlify.com/qdrant/qdrant/advanced/quantization), [Qdrant single-node benchmark](https://qdrant.tech/benchmarks/single-node-speed-benchmark/)
- Consumer GPU LLM: RTX 4090 8B Q4 ~128 tok/s single-stream and ~2,700 tok/s aggregate at 300 concurrent (vLLM, 8B BF16); RTX 5090 ~200 tok/s on 8B, ~45 tok/s on 70B 4-bit (offloaded) — [XiongjieDai benchmarks](https://github.com/XiongjieDai/GPU-Benchmarks-on-LLM-Inference), [markaicode vLLM 4090](https://markaicode.com/benchmarks/vllm-llama-31-rtx-4090-throughput-benchmark/), [llmhardware 5090 vs 4090](https://llmhardware.io/guides/rtx-5090-vs-4090-llm-guide)

### Inferences
- Tier 1, single workstation (≤10 concurrent users, 10k-30k docs): 16-24 core CPU, 64-128 GB RAM, one RTX 5090 (32 GB) or 4090 (24 GB), 2-4 TB NVMe. Run Qdrant or Postgres+pgvector (vectors <5 GB), TEI with Qwen3-Embedding-0.6B/4B or bge-m3 and bge-reranker-v2-m3 on GPU (<3 GB VRAM), and a 8B-14B instruct model in Q4-Q6 via llama.cpp/vLLM (8-12 GB VRAM) => ~100-200 tok/s single stream, ~1,500-2,500 tok/s aggregate. Initial ingest of 1M pages: ~1-2 days of PDF parsing (parallelize over CPU cores) and ~1-3 h of embedding on the GPU.
- Tier 2, small on-prem server with one GPU (50-100 users, up to 100k docs): 32-64 cores, 256 GB RAM, one 80-96 GB GPU (H100/H200 or RTX 6000 Pro Blackwell 96 GB; L40S 48 GB if a ≤32B model suffices). A 70B FP8 model on H100 gives ~1,500-1,850 tok/s aggregate ≈ 50-70 concurrent generations at 25-50 tok/s each; embedding/rerank share the GPU (few GB). Keep vectors in RAM with scalar quantization (<10 GB for 5M x 1024-d). Qdrant plus Postgres for metadata is a two-container footprint.
- Tier 3, cloud (100-200 users): either two GPU nodes (A100/H100 80 GB) behind vLLM with Qdrant/pgvector on a 32-64 GB RAM VM, or hybrid: self-host embeddings/ANN/rerank on one cheap GPU (L4/A10G class, $0.5-1/h) and call Claude/OpenAI for generation. Break-even: an H100 at ~$2-3/h (~$1,500-2,200/month) produces up to ~1,850 tok/s ≈ 160M output tokens/day at full load; the same tokens via Haiku 5.5 would cost ~$80/day at list, via Sonnet 5.5 ~$1,600/day. Below ~10-20M generated tokens/day (typical for 200 engineers), API generation with Haiku/Sonnet-class models is cheaper and has no ops burden; above that, or where documents cannot leave the premises, the on-prem GPU wins.
- Embedding via API vs local: one-time ingest of ~1.6B tokens costs ~$30-$200 by API (voyage-4-lite to OpenAI 3-large) versus a few GPU-hours locally; both trivial. The reason to self-host embeddings is data residency and the need for re-embedding when swapping models, not cost. Query-time rerank via API ($2-2.50 per 1k searches) at 200 users x 50 queries/day = $20-25/day; a local GPU reranker is free at the margin.
- Latency budget (local, Tier 1/2): query embed 10-30 ms GPU, hybrid ANN+BM25 5-20 ms, rerank 50 pairs 50-100 ms GPU (2 s on CPU), generation TTFT 100-300 ms then 25-150 tok/s => first token well under 500 ms. API path adds ~0.5-1.5 s TTFT variance.

### Gaps

- Current spot/on-demand H100/L40S cloud prices were not verified in this session (the $2-3/h figure is from general 2025-26 market knowledge, not a fetched source).
- RTX 6000 Pro Blackwell 96 GB and Strix Halo numbers were not found; Blackwell datacenter (B200) LLM throughput only appears via InferenceX pages not fetched.
- Anthropic prices were taken from a bundled skill reference, not the live pricing page.
