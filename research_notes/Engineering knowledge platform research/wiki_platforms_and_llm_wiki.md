# Wiki platforms and the "LLM wiki" pattern for an engineering knowledge platform (state as of October 2026)

Scope note: this covers the human-editable "wiki" half of the platform (where an LLM drafts pages from thousands of ingested documents, engineers across non-software disciplines edit them, and a chat assistant answers from the wiki). Research method: web search plus direct fetches of GitHub repos, release pages and Karpathy's gist. Several official doc sites (docmost.com, getoutline.com, bookstackapp.com, mediawiki.org, obsidian.md/help.obsidian.md, extensions.xwiki.org, wz-it.com, professional.wiki, backstage.spotify.com) were unreachable from this environment (DNS blocked) and the search budget ran out before the last round of verification, so some facts below rest on GitHub pages, release notes and secondary comparison articles. Unverified items are moved to the Gaps sections rather than stated as fact.

## Key Question 1: Which wiki platform gives the best combination of easy editing for non-technical engineers, strong API for AI agents to write pages, good permissions, and self-hosting?

### Takeaway
As of Oct 2026 the realistic shortlist for "Notion-like editing + agent-writable API + permissions + self-host" is Outline (most mature API/MCP, real-time editor, but BSL 1.1 source-available), Docmost (AGPL core, real-time editor, but AI/MCP/vector-search features are enterprise-licensed), BookStack (MIT, very stable REST API, WYSIWYG+Markdown, but no real-time co-editing), and XWiki (LGPL, Java, strongest structured-data and the only one with a first-party RAG/LLM extension incl. an MCP server). MediaWiki remains the scale/provenance benchmark but its editing UX is the hardest for non-technical users; Wiki.js 3.0 is still beta after 5 years and is a poor bet.

### Inferences
- For *non-software engineers* the decisive UX properties are: a Notion-style block/WYSIWYG editor, real-time co-editing (so two people never fight over a page lock), inline comments, and a page tree. Outline and Docmost satisfy all four; BookStack satisfies the first (new WYSIWYG) but not real-time; XWiki has a WYSIWYG but a heavier, older UI; MediaWiki requires wikitext or VisualEditor and is the steepest.
- For *agent writability*, Outline is currently the only self-hostable wiki whose first-party release notes show a maintained MCP server, Markdown-in/Markdown-out tools, optimistic-concurrency (`lastRevision`) on `documents.update`, scoped API keys and webhooks. Docmost has MCP/AI only in the paid EE; BookStack has a stable REST API but agent access is via community MCP servers; XWiki's LLM extension includes an MCP server per WZ-IT (unverified first-hand).
- Licensing trade-off: BookStack (MIT), XWiki (LGPL), MediaWiki (GPL), Docmost core (AGPL) are OSI open source; Outline is BSL 1.1 which is fine for an internal engineering wiki (the only forbidden use is offering it as a hosted document service to third parties) but is not "open source" and every release pushes the Apache conversion date out four more years.
- Weighted for this use case (easy editing > agent API > permissions > open licence), the ranking is: Outline (best UX+API, licence caveat) > Docmost (open core but pay for AI/MCP) > BookStack (fully open, simple, no live co-editing) > XWiki (most capable, heaviest, only first-party RAG) > MediaWiki (scale and provenance champion, worst UX for this audience) > Wiki.js (stalled).

## Key Question 2: Is a markdown-in-git wiki (with pull-request-style review) better or worse than a database-backed wiki when AI generates most first drafts? (Includes the requested dedicated evaluation of Obsidian and structured-markdown successors)

### Takeaway
Markdown files with structured frontmatter remain the best substrate for LLM agents (every 2026 "LLM wiki" implementation uses them, and Karpathy's gist is explicitly files + git), but as of Oct 2026 no file-based tool offers a server-side API, multi-user permissions and a friction-free editor for non-technical users at once; Obsidian in particular still has no headless API. The practical answer is a hybrid: keep markdown+frontmatter as the canonical store that agents write to, and put a web wiki with a proper API/editor on top — or, if you accept vendor-shaped storage, adopt a database-backed wiki (Outline or Docmost) and treat its Markdown export/API as the agent surface.

### Cited Findings

#### The "LLM wiki" pattern (Karpathy) and what it assumes about the store
- Karpathy's gist "LLM Wiki" (created April 2026; the gist page shows Apr 4, secondary coverage says Apr 2) is an "idea file" meant to be pasted into an agent. Core: "the LLM incrementally builds and maintains a persistent wiki"; "the wiki is a persistent, compounding artifact"; "Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase." Three layers: immutable raw sources, LLM-owned markdown wiki, and a schema (CLAUDE.md/AGENTS.md) that user and LLM "co-evolve". Workflows: ingest (one source may touch 10–15 pages; he prefers one source at a time with supervision), query (answers "with citations"; valuable answers "filed back into the wiki as new pages"), lint (contradictions, stale claims, orphan pages, missing cross-refs). `index.md` is a categorized catalog read first on every query; `log.md` is append-only with parseable prefixes like `## [2026-04-02] ingest | Article Title`. Tools: Obsidian, Claude Code/Codex/OpenCode, `qmd` (local BM25/vector search with LLM re-rank, CLI + MCP) or a naive search script, Git "for version history and collaboration", Marp, matplotlib. Scale: index approach "works surprisingly well at moderate scale (~100 sources, ~hundreds of pages)"; larger wikis "may need proper search tooling". Limitations he notes: "LLMs can't natively read markdown with inline images in one pass"; the document is "intentionally abstract"; no formal provenance system beyond citations, git history and the log — [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f).
- Gist comment thread (Oct 2026) critiques: a controlled 2-repo/8-run experiment found the best accuracy from "wiki page + prompt excerpts + an edit-time rule gate" (author says not a general benchmark); another commenter measured ~72% of ingest tokens going to decisions rather than writing, and a small typed classifier raised correct-note retrieval from 62% to 89% on 525 documents; a podcast-wiki builder's lessons: "avoid near-duplicate pages, never silently overwrite, rewrite summaries instead of appending, and run periodic merge passes"; another argues the wiki should record only significant decisions and open questions with owners, not act as agent memory. Derivatives named: llmwiki (SQLite+Markdown), llm-wiki-v2 (AGPL, Ollama), MindBase 0.4.6 (MIT, broken-link and near-duplicate checks, query logging), Nimbalyst Wiki (MIT Claude Code/Codex plugin), Awesome LLM Wiki list — [Karpathy gist comments](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f).
- Secondary coverage: VentureBeat frames it as "bypasses RAG" with no vector DB at personal scale and periodic "linting" passes — [VentureBeat](https://venturebeat.com/data/karpathy-shares-llm-knowledge-base-architecture-that-bypasses-rag-with-an); Towards AI reports the community split ("RAG is dead" vs "a cache layer with a new name") and flags "enterprise scalability is the elephant in the room: no RBAC, no ACID transactions, no concurrency controls" — [Towards AI](https://pub.towardsai.net/andrej-karpathy-killed-rag-or-did-he-the-llm-wiki-pattern-7824d876e790); Implicator says the post drew ~16 million views — [Implicator](https://implicator.ai/karpathys-llm-wiki-got-16-million-views-the-code-isnt-the-point-2/).

#### Implementations of the pattern (all file-based)
- **lucasastorian/llmwiki** (Apache-2.0, Python 3.11+/Next.js; SQLite+filesystem locally or Postgres+S3 hosted; ~1.7k stars): ingest via web upload, folder watcher, or Chrome clipper; formats PDF, DOCX/PPTX, XLSX, HTML, MD, images (LibreOffice for Office, Mistral API for PDF OCR); Claude writes via MCP tools `create/edit/append/delete/lint/search/read`; "writes go to the source of truth first, then the search index updates"; nightly "Claude Routine" updates autonomously; `create` adds footnote citations back to sources; search can query the citation graph for stale/uncited pages; `lint` checks citation resolution; `edit` is exact-text find/replace; **no human approval step described**; multi-user unclear (hosted mode has sign-in; local mode single loopback workspace); full-text SQLite search, no vector search described — [llmwiki repo](https://github.com/lucasastorian/llmwiki).
- **NicholasSpisak/second-brain** (~752 stars; license not shown): `raw/` folder in, `/second-brain-ingest` discusses takeaways then writes `wiki/sources/`, `entities/`, `concepts/`, `synthesis/`, `index.md`, `log.md`; `/second-brain-lint` checks index consistency and broken `[[wikilinks]]` (suggested every 10 ingests); user is "curator"; no formal approval or citation mechanism — [second-brain repo](https://github.com/NicholasSpisak/second-brain).
- **Auto LLM Wiki** (Obsidian plugin): sends only new/changed raw files to an OpenAI-compatible endpoint, generates a "structured JSON change plan", previews proposed changes, and applies "only after user confirmation"; raw sources read-only — [Obsidian plugin listing](https://community.obsidian.md/plugins/auto-llm-wiki). **llm wiki** (enduserlab, MIT) adds YAML frontmatter, confidence scores, memory tiers, graph edges, with ingest/query/lint/crystallize ops — [listing](https://community.obsidian.md/plugins/llm-wiki). **pensar** (R) seeds vaults with CLAUDE.md and AGENTS.md so Claude Code and Codex share instructions — [CRAN](https://cran.nics.utk.edu/cran/web/packages/pensar/refman/pensar.html). A Claude Code skill turns an agent into "a disciplined wiki maintainer" for an Obsidian vault — [tessl registry](https://tessl.io/registry/skills/github/alirezarezvani/claude-skills/llm-wiki). An Indie Hackers author built the same with a CLAUDE.md "defining the folder structure, six core workflows, and ... conventions (frontmatter, wikilinks, log format)" — [Indie Hackers](https://www.indiehackers.com/post/i-got-tired-of-my-obsidian-vault-rotting-so-i-built-an-ai-to-maintain-it-open-sourcing-my-llm-wiki-7d05b1ebe1).
- **deepwiki-open** (AsyncFuncAI, MIT, ~18.2k stars): code repositories only (GitHub/GitLab/Bitbucket), OpenAI/Gemini/Ollama/OpenRouter providers, "Deepwiki-Open 2.0 (Grok Wiki is now live)"; no human-editing workflow — [deepwiki-open repo](https://github.com/AsyncFuncAI/deepwiki-open). OpenDeepWiki (C#/TypeScript) is another — [GitHub topic](https://github.com/topics/deepwiki). Not applicable to document corpora.

#### Dedicated evaluation: Obsidian for team use (Oct 2026)
- **Commercial licence**: since Feb 2025 "the Obsidian Commercial license is optional. Anyone can use Obsidian for work, for free"; older help pages describing a mandatory licence for companies with 2+ employees are historical — [Obsidian blog "Free for work"](https://obsidian.md/blog/free-for-work/); [old commercial-license page](https://help.obsidian.md/Teams/Commercial+license).
- **No server-side API**: the official Obsidian CLI shipped in v1.12 (Feb 2026) but "is not headless. #### Docs-as-code (MkDocs/Docusaurus/Sphinx) with PR review
- Vendor/practitioner sources agree: Git-based review gives diffs alongside code and CI checks (links, style) before merge, and "enforcing review before publishing improves quality"; but "product managers, legal reviewers, and support leads still need a practical way to review docs changes without becoming Git users"; a wiki "suits an organization with no existing Git workflow, since introducing Git only for docs adds a system to maintain"; Git "can't flag an untouched page that should have changed too"; workaround: a browser editor that "opens a pull request behind the scenes" — [Mintlify governance](https://www.mintlify.com/library/documentation-governance-with-git-and-branch-protection); [Mintlify what-is-docs-as-code](https://www.mintlify.com/library/what-is-docs-as-code); [Slite](https://slite.com/ja/learn/docs-as-code); [Computing](https://computing.co.uk/opinion/4034360/docs-code-answer-development-teams-perennial-documentation-woes).
- ReadMe's AI-docs guidance: treat AI output "as a proposal on a branch, with a visible diff against the original page"; "auto-publishing drafts is what erodes trust" — [ReadMe](https://readme.com/resources/ai-writer-review-workflow).

### Inferences
- **Why markdown wins for the agent side**: every working LLM-wiki implementation found (Karpathy, llmwiki, second-brain, Auto LLM Wiki, MindBase, Nimbalyst) operates on plain markdown files with frontmatter/wikilinks, uses git or an append-only log as history, and uses exact-text edits — because agents can read, grep, diff and rewrite files natively and the "schema" (CLAUDE.md) travels with the repo. Database-backed wikis force the agent through an API with the vendor's document model (Notion blocks, ProseMirror JSON) and lossy Markdown round-trips.
- **Why markdown-in-git loses for the human side**: the audience here is fluid/electrical/civil/structural engineers. Git PR review (even via a browser editor) adds concepts (branches, conflicts, merge) that the docs-as-code literature itself says non-developers resist; none of the file-based tools (Obsidian, SilverBullet, Foam, Dendron, Quartz) offer per-page permissions or an audit trail of who edited what beyond git blame; Obsidian needs a desktop app per editor plus a paid/hosted relay for live co-editing; Logseq DB is beta with data-loss warnings; SiYuan is single-writer; Trilium is single-user. Dendron is dead and Foam is alpha.
- **The AI-first-draft workload changes the calculus in favour of files + review, not against it**: when 80–90% of edits are machine-generated, you need (a) cheap diffs, (b) a staging area where drafts sit before publication, (c) a way to regenerate a page from sources without clobbering human edits, and (d) a schema the agent obeys. Git branches + frontmatter (`status: draft|reviewed`, `sources: [...]`, `generated_by`, `reviewed_by`) give all four for free; database wikis give (a) and partially (b) via drafts/revisions (Outline `lastRevision`, BookStack changelog messages, Docmost page history) but (c) and (d) must be built in your pipeline.
- **Recommendation (see end of this section)**: keep the structured-markdown model as canonical and put a web wiki + API on top; do not adopt a desktop-first tool (Obsidian/Logseq/SiYuan/Anytype) as the team's primary wiki.

#### Recommendation: which path, and the best concrete option for each
- **Path A — keep "markdown files with structured frontmatter" and add a web wiki/API on top (recommended for this project).** Best concrete option today: a git repository of markdown + YAML frontmatter as the canonical store (agents write it with Claude Code/Codex per the Karpathy schema), **SilverBullet** as the self-hosted web front end for browsing and lightweight editing (MIT, Rust server, files-on-disk, HTTP space API, OIDC, built-in object/query language that replaces Dataview-style queries — [SilverBullet repo](https://github.com/silverbulletmd/silverbullet)), with git as the review queue (draft branch → reviewer approves → merge → publish) and an optional Quartz static build for read-only consumers — [Quartz repo](https://github.com/jackyzha0/quartz). Caveat: SilverBullet has no documented real-time co-editing or page-level permissions; if those are mandatory, swap the front end for Outline/Docmost and sync markdown both ways (Path B hybrid). Obsidian stays as an optional power-user client on the same repo (free for work since Feb 2025 — [Obsidian blog](https://obsidian.md/blog/free-for-work/)) but must not be the system of record because it has no headless API.
- **Path B — move to a database-backed wiki.** Best concrete option: **Outline** (real-time ProseMirror-style editor, revision history, scoped API keys, webhooks, first-party MCP with Markdown I/O and `lastRevision` concurrency, OKF/PDF/web import; BSL 1.1 is acceptable for an internal tool) — [Outline releases](https://github.com/outline/outline/releases); [Outline LICENSE](https://raw.githubusercontent.com/outline/outline/main/LICENSE). If an OSI licence is a hard requirement, **BookStack** (MIT, stable REST API with per-call changelog messages, WYSIWYG + Markdown editors, mature permissions, but no live co-editing) — [BookStack releases](https://github.com/BookStackApp/BookStack/releases) — or **Docmost** (AGPL core; budget for the enterprise licence if you want its MCP/AI search) — [Docmost releases](https://github.com/docmost/docmost/releases). In Path B the agent writes via API; the git/markdown layer becomes a nightly export for backup, diffing and re-indexing.

## Key Question 3: How do existing projects handle "document uploaded -> LLM proposes wiki changes -> human approves"? Established patterns for review queues, provenance/citations, conflict handling?

### Takeaway
There is no standard; the field has converged on a few recurring mechanisms — candidate/draft-first writes with explicit accept/reject, immutable raw sources with footnote citations back to them, a schema file that fixes page/citation conventions, status fields (developing → mature → stale), lint passes for contradictions/duplicates/broken links, and an append-only log — but most open-source LLM-wiki tools (llmwiki, second-brain) skip the human approval step entirely, and only one plugin (Auto LLM Wiki) and Spotify's internal Backstage "wiki pages" implement a true review queue.

### Cited Findings
- **Spotify Backstage "wiki pages"** (closest to the target loop): a seed-and-maintain model where the system proposes pages and "a workspace member accepts, rejects, or dismisses each suggestion after comparing it against the cited resources"; a separate schema page "sets the conventions for source citations and page structure"; docs state generation "does not remove the need for review" — [Backstage docs](https://backstage.spotify.com/docs/xirp/workspaces/wiki-pages) (page unfetchable; from search summary).
- **ReadMe**: "A review workflow that works treats AI output as a proposal, not a commit" — proposal on a branch with visible diff; auto-publishing erodes trust — [ReadMe](https://readme.com/resources/ai-writer-review-workflow).
- **Auto LLM Wiki (Obsidian)**: structured JSON change plan → preview → apply only after confirmation; raw sources read-only — [plugin listing](https://community.obsidian.md/plugins/auto-llm-wiki).
- **An LLM-wiki MCP server** implements "candidate-first writes that need explicit human approval before a page, index update, or export is finalized" — [mcpmarket llm-wiki](https://mcpmarket.com/zh/server/llm-wiki-5).
- **dbt-wiki skill certification loop**: pages start "developing" (LLM-distilled, unverified), become "mature" only after human confirmation, and "re-enter the queue when flagged as stale" — [skills.sh review skill](https://www.skills.sh/kouko/monkey-skills/review).
- **llmwiki provenance**: `create` adds footnote citations to sources; citation graph queryable for "what cites what and which pages are stale or uncited"; `lint` checks citation resolution; but nightly routine updates pages autonomously with no approval gate; conflict handling not described, filesystem is source of truth and external edits are re-indexed by a watcher — [llmwiki repo](https://github.com/lucasastorian/llmwiki).
- **Karpathy**: raw sources immutable; answers cite; "filed back" answers compound; lint for contradictions/stale claims/orphans; log.md as audit trail; he prefers one-source-at-a-time ingestion "with close supervision"; commenters' lessons: "never silently overwrite", "rewrite summaries instead of appending", "run periodic merge passes", avoid near-duplicates — [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f).
- **Wikipedia as cautionary precedent**: reviewers "flooded non-stop with horrendous drafts" from AI with "lies and fake references"; response was WP:NOLLM (Mar 2026) and speedy deletion of blatant AI drafts without the 7-day review — [Beutler Ink](https://beutlerink.com/blog/wikiwise/crack-down-on-ai); [Wikipedia AI article](https://en.wikipedia.org/wiki/Artificial_intelligence_in_Wikimedia_projects). A 2026 paper proposing "Spectrum of AI Involvement" tags notes MediaWiki edit tags (visualeditor, mobile edit, reverted) "provide only a partial view of tool activity", tool use is "inconsistently recorded", and "some editors avoid tagging AI use to dodge responsibility for errors" — [Clarkson DHOW26 paper](https://lin-web.clarkson.edu/~jmatthew/publications/DHOW26_errata.pdf).
- **Grokipedia** apparently stopped updating articles after 24 Apr 2026 without announcing it — cited as a reason to make pipeline status visible — [Lawfare](https://www.lawfaremedia.org/article/grokipedia-stopped-reviewing-edits-in-april.-it-didn-t-tell-anyone).
- **Concurrency primitives available in wikis**: Outline `documents.update` takes optional `lastRevision`; MCP mutations use Markdown; collaboration connections re-authorized on access change — [Outline releases](https://github.com/outline/outline/releases). BookStack page create/update can carry a changelog message — [BookStack releases](https://github.com/BookStackApp/BookStack/releases).
- **Outline maintainers refuse AI-generated PRs** to the codebase — a signal of how maintainers view unreviewed AI drafts — [Outline repo](https://github.com/outline/outline).

### Inferences
- A workable, evidence-backed loop for this project: (1) upload → immutable `raw/` store with document id and hash; (2) agent produces a *change plan* (list of pages to create/modify + rationale) rather than direct writes; (3) each proposed page is written as a draft (git branch, or wiki draft/unpublished state) with frontmatter `status: proposed`, `sources: [doc-id#chunk]`, `generated_by`, `base_revision`; (4) a review queue UI shows the diff against the current page and the cited passages side by side (Backstage/ReadMe pattern); (5) accept → publish/merge and set `reviewed_by/at`; reject/dismiss → log the reason so the agent's schema can be tuned; (6) lint jobs run on a schedule for contradictions, duplicates, orphan pages and unresolved citations (Karpathy/llmwiki/MindBase pattern); (7) a human edit to a published page sets `human_edited: true` so later regenerations propose rather than overwrite.
- Provenance should be stored twice: inline footnotes in page body (readable by humans and LLM) and structured in frontmatter (machine-queryable for "which pages cite document X" when X is updated or withdrawn).
- Conflict handling: file-based systems rely on git merge or "never silently overwrite"; database wikis offer optimistic concurrency (`lastRevision`) — the agent should always read-then-write with the revision token and fall back to opening a new proposal when it loses the race.

### Gaps
- No open-source project was found that implements the full loop (ingest → proposal → review queue → publish → re-index) for a *multi-user* wiki; Backstage's implementation is Spotify-internal and its docs were not fetchable.
- No published data on reviewer throughput or acceptance rates for AI-drafted wiki pages in engineering organizations.
- No source describes conflict resolution between simultaneous human real-time edits and an agent API write in Outline/Docmost; only the `lastRevision` parameter and a mis-attribution bug fix are documented.

## Key Question 4: How should the wiki and the vector/search index stay in sync when pages change?

### Takeaway
Community practice (no authoritative standard found) is event-driven per-page re-indexing: webhook on edit → delete all chunks for the page id → re-chunk and re-embed → upsert, gated by a content hash so unchanged pages are skipped, with deletes propagated immediately and a periodic reconciliation sweep to catch missed events. The wiki should remain the source of truth; llmwiki's rule "writes go to the source of truth first, then the search index updates" is the right ordering.

### Cited Findings
- Event-driven flow: initial bulk ingestion, then a monitor per source, then a change event triggers an update "to only the affected vector entries"; argued to be faster, cheaper and more reliable than scheduled re-crawls — [PageCrawl](https://pagecrawl.io/blog/keep-rag-pipelines-fresh-web-monitoring).
- Delete-then-insert per page id, then normal chunk-and-embed; the n8n Pinecone node cannot filter deletions by metadata so raw HTTP is used — [growwstacks n8n guide](https://growwstacks.com/blog/build-self-updating-rag-bot-n8n).
- Hash chunks/pages and re-embed only on hash change: "a typo fix in one paragraph should not trigger re-embedding of a whole handbook" — [kapa.ai](https://www.kapa.ai/library/how-to-keep-a-rag-knowledge-base-in-sync-with-changing-docs); a local wiki implementation keys staleness on content hash rather than mtime so git checkouts/cloud sync don't trigger false rebuilds — [ragIndex.ts example](https://lmstudio.ai/zexigh/kwikines/files/src/ragIndex.ts).
- Deletions are the worst staleness class: "deleted, still indexed — the source doc is gone but the vector store still serves it" → ghost citations — [twig.so](https://www.twig.so/dev/rag-scenarios-and-solutions/accuracy/stale-data).
- Webhooks give near-zero staleness but add "webhook reliability and burst load handling" concerns; pair with a nightly reconciliation that diffs hashes and purges orphans — [tray.ai](https://tray.ai/automate/knowledge-base-to-vector-sync/); [Kestra blueprint](https://kestra.io/blueprints/rag-knowledge-base-vector-reconciliation); `ragfresh` PyPI package exists for this — [PyPI](https://pypi.org/project/ragfresh/).
- Platform hooks available: Outline has webhooks (editable without re-entering signing secrets as of v1.10.1) and excludes archived docs from MCP search — [Outline releases](https://github.com/outline/outline/releases); Docmost EE ships its own Turbopuffer/pgvector "AI search" driver — [Docmost releases](https://github.com/docmost/docmost/releases); XWiki's LLM Application requires a separate "Index for the LLM Application" to be installed for RAG — [XWiki LLM project](https://extensions.xwiki.org/xwiki/bin/view/Extension/LLM/); MediaWiki `AutoLlmsTxt` regenerates llms.txt "when pages change" — [Extension:AutoLlmsTxt](https://www.mediawiki.org/wiki/Extension:AutoLlmsTxt); llmwiki updates its SQLite index after each write and re-indexes external edits via a file watcher — [llmwiki repo](https://github.com/lucasastorian/llmwiki).
- Karpathy's position for moderate scale: index.md + grep/`qmd` (BM25 + vector with LLM re-rank) instead of embedding infrastructure; "larger wikis may need proper search tooling" — [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f).

### Inferences
- With thousands of source documents plus an LLM-written wiki, run two indexes: (1) raw documents (chunked, embedded once, keyed by doc id + hash) for provenance lookups, and (2) wiki pages (re-embedded on publish only, not on every draft keystroke) for the chat assistant. Index only *published/reviewed* pages so the assistant never cites an unapproved AI draft; store `status`, `page_id`, `revision`, `source_ids` as chunk metadata so answers can carry both wiki citation and underlying document citation.
- In a git-canonical design the "webhook" is a post-merge CI job: compute hash per file, diff against the index manifest, delete+upsert changed, delete removed; in a DB-wiki design subscribe to `documents.update/delete/archive` webhooks and keep the nightly reconciliation regardless.

### Gaps
- No authoritative or peer-reviewed reference on wiki→vector synchronization; all sources are vendor blogs or small tools.
- Outline's webhook event catalog and Docmost/BookStack webhook support were not verified from primary docs.

## Key Question 5: Known pain points (performance at scale, editor bugs, migration lock-in)?

### Takeaway
Documented 2026 pain points: Wiki.js's five-year-stalled 3.0 and slowing commits; Outline's BSL licence, hard dependency on an external IdP, and recurring editor/revision bugs visible in its changelog (though actively fixed); Docmost paywalling AI/MCP/SSO/SCIM; BookStack's lack of real-time co-editing; Logseq DB's beta data-loss warnings and product stagnation; AFFiNE's pre-1.0 breaking changes; Obsidian's desktop-only, non-headless architecture; and, for AI-drafted content generally, reviewer flooding and fabricated citations (Wikipedia). Lock-in is lowest for markdown-file systems and MIT/LGPL wikis, highest for block/CRDT stores (AFFiNE, Anytype, Notion) and source-available licences.

### Cited Findings
- Wiki.js: 3.0 "NOT FOR PRODUCTION USE" beta — [repo](https://github.com/requarks/wiki); announced 2021, alpha since, "Beta Release: TBD", tracker shows "0 commits in the last 3 months" — [WZ-IT](https://wz-it.com/en/blog/bookstack-wikijs-xwiki-docmost-comparison/); [ideaproof](https://ideaproof.io/open-source/project/wiki-js).
- Outline: BSL 1.1 not open source, change date 2030-10-12 — [LICENSE](https://raw.githubusercontent.com/outline/outline/main/LICENSE); must configure OAuth/OIDC, no local login — [ossalt](https://ossalt.com/guides/how-to-self-host-outline-notion-alternative-team-wiki-2026); recent fixes for "revisions sometimes attributed to the wrong user during collaborative edits", revision scroll resets, "diffs are skipped when they are too expensive to compute", N+1 queries, memory use — [releases](https://github.com/outline/outline/releases).
- Docmost: AI requires enterprise licence — [Docmost AI docs](https://docmost.com/docs/user-guide/ai); SSO/SCIM not in free tier — [Contabo](https://contabo.com/blog/best-self-hosted-wiki-tools/); MCP OAuth marked EE — [releases](https://github.com/docmost/docmost/releases); 240 open issues / 116 open PRs — [repo](https://github.com/docmost/docmost).
- BookStack: no real-time collaboration — [Contabo](https://contabo.com/blog/best-self-hosted-wiki-tools/); multiple 2026 security fixes around attachments on drafts and API leaking recycled-bin content — [releases](https://github.com/BookStackApp/BookStack/releases).
- XWiki LLM extension: "still in beta"; users want traceability of which questions get good answers — [XWiki forum](https://forum.xwiki.org/t/ai-llm-extension-add-traceability-observavility/18705); official page "lists partly outdated requirements" — [WZ-IT](https://wz-it.com/en/blog/xwiki-ai-llm-setup/).
- Logseq DB: "data loss is possible", RTC alpha — [repo](https://github.com/logseq/logseq); "early beta with real data-loss risk", sync paid/invite-only, "stagnated for so long" — [kompozy](https://kompozy.io/reviews/logseq-2-0).
- AFFiNE self-hosted "pre-1.0 and prone to breaking changes" — [selfhosting.sh](https://selfhosting.sh/compare/affine-vs-appflowy/); AppFlowy free self-host is single-user — [Sliplane](https://sliplane.io/blog/5-awesome-appflowy-alternatives).
- Obsidian CLI "is not headless" — [dsebastien](https://www.dsebastien.net/the-complete-guide-to-the-obsidian-cli-everything-you-can-do-from-the-terminal/); Relay permissions: "anyone with the share key can join", stricter sharing "planned" — [Relay repo](https://github.com/No-Instructions/Relay).
- Quartz: "if you cannot navigate a file system or use Git, this tool will be too difficult to maintain" — [aiindigo](https://aiindigo.com/blog/building-your-digital-garden-a-deep-dive-into-quartz-in-2026).
- Notion API: 3 req/s per integration; block model with no SQL surface — [Unblocked](https://getunblocked.com/blog/best-knowledge-base-ai-agents/).
- LLM-wiki pattern at scale: Karpathy's own scope is ~100 sources; "no RBAC, no ACID transactions, no concurrency controls" — [Towards AI](https://pub.towardsai.net/andrej-karpathy-killed-rag-or-did-he-the-llm-wiki-pattern-7824d876e790); image handling requires a separate pass — [gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f); ~72% of ingest tokens spent on routing decisions in one measurement — [gist comments](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f).
- AI drafts: reviewers flooded, fabricated references, speedy-deletion response — [Beutler Ink](https://beutlerink.com/blog/wikiwise/crack-down-on-ai).

### Inferences
- Migration lock-in ranking (lowest → highest): plain markdown+git (Obsidian/SilverBullet/Foam/Quartz) < BookStack/XWiki/MediaWiki (open licences, mature export) < Outline/Docmost (Markdown export exists but ProseMirror/Yjs internal model, BSL or EE components) < AFFiNE/Anytype/Logseq DB (CRDT/JSON block stores, young or non-OSI licences) < Notion/Confluence (SaaS, block APIs, rate limits).
- Performance: none of the self-hostable Notion-likes publish scale numbers; MediaWiki is the only candidate with proven multi-million-page deployments (Wikipedia) but that was not re-verified this session. For "thousands of documents → likely tens of thousands of wiki pages" any of Outline/BookStack/XWiki/MediaWiki on Postgres/MySQL should be adequate; the risk is in the editor (large-document rendering) and search, not storage.

### Gaps
- Direct evidence on Outline/Docmost/BookStack performance at 10k+ pages or 500+ concurrent editors was not found; the planned search was blocked by the search budget.
- MediaWiki 1.4x release status, VisualEditor state and REST API edit capabilities in 2026 were not verified (mediawiki.org unreachable).
- Reddit r/selfhosted threads were not retrieved; all comparison material came from vendor/hosting-company blogs (Docmost, Elestio, Contabo, Nuclino, Sliplane, SSD Nodes), which should be read as directional.
