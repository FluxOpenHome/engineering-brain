## KQ1. What already exists that does "check this supplier document against these specs" with an LLM, and how accurate is it?

### Takeaway
As of October 2026 no mainstream requirements-management (RM) vendor ships a product whose core job is "take a supplier datasheet/proposal and produce a clause-by-clause compliance verdict with evidence." The RM vendors (IBM, Jama, Siemens Polarion, Altium/Valispace, QRA, Modern Requirements, Reqi) ship LLM features aimed at *authoring quality* (INCOSE/EARS rule scoring, rewriting, similarity, consistency between linked items). The clause-level "document vs. spec" use case is served instead by (a) construction submittal/spec-review agents (Datagrid/Procore, Ichi, Autodesk Assistant, Document Crunch/Trimble), (b) GovCon proposal "shredding"/compliance-matrix tools (GovDash, GovEagle, Loopio), (c) tiny open-source prototypes (CompChecker, ctsm, Compliance_Checker), and (d) academic pipelines (AICCE, CTRAG, Graph-RAG). Accuracy claims are almost entirely vendor-reported and unverified; the only independently reported clause-level numbers (construction/regulatory domain) range from F1 0.67–0.93 for clause extraction and precision ~62–72% / recall ~72–85% for compliance verdicts, with a documented tendency to miss non-compliant cases.

**Open-source / GitHub prototypes that do the exact job**
- **epifaneia/ctsm** ("Customer-to-Supplier Mapping"): takes a customer ReqIF export from Polarion plus supplier PDFs and writes back the same ReqIF with per-requirement Status (from the file's own enum), Rationale (analysis + citations with document/page/section) and "Comments to the customer." Five-step pipeline (cleaning, context, input guardrail, processing, output guardrail) in which only "processing" calls the model; BM25 retrieval; constrained response schema; each quote verified against source; unverified verdicts stay "open" and are flagged for human review. Local by default (Ollama qwen2.5 14B recommended), Gemini optional. Reported on a hand-labelled 9-requirement set against the public STM32 RM0008 manual: Gemini 9/9, qwen2.5:14b 8/9, qwen2.5:7b 7/9, all with 0 false "compliant." Apache-2.0, 0 stars, 4 commits (2026) — [github.com/epifaneia/ctsm](https://github.com/epifaneia/ctsm); companion [epifaneia/reqif-extractor](https://github.com/epifaneia/reqif-extractor) extracts PDF specs into Polarion-importable ReqIF
- **Aaryan-Chokshi/CompChecker**: FastAPI + Dash; uploads policy docs and supplier specs (TXT/MD/CSV/TSV/DOCX/text-PDF); tables/rows become chunks; local HF embeddings (gte-large-en-v1.5) in Qdrant; Ollama (default gpt-oss:20b-cloud) makes JSON judgments validated by Pydantic; runs *reverse checks* so omitted policy obligations surface; output is a matrix with one row per obligation, rating in {satisfied, partial, not_satisfied, insufficient_evidence, not_applicable}, extent %, self-reported confidence 0–1 ("not a calibrated probability"), explanation, validated evidence citations, overall status {compliant, non_compliant, needs_review}, and a supplier clarification sheet (MD/DOCX/PDF). **Academic pipelines and reported accuracy**
- AICCE (arXiv 2604.03330, accepted IEEE Trans. on AI; Rahman, Lopez, Mim, Farthing, Battle, Buckley, Hariri): checks IPv6 protocol compliance using retrieval of the relevant spec section plus multiple parallel LLM agents; if all section agents return Yes the packet is accepted, otherwise a *structured debate* resolves conflicts and surfaces clause-level justifications; a second pipeline converts clauses to executable Python for dataset-scale checks; abstract reports accuracy/F1 "up to 99%" across sixteen generative models. A third-party review notes the 99% claim lacks visible evaluation detail — [arXiv 2604.03330](https://arxiv.org/abs/2604.03330); [Pith review](https://pith.science/paper/2604.03330)
- Graph-RAG + prompt engineering for requirement traceability & compliance (arXiv 2412.08593): builds a graph from regulatory texts, standards and SRS; tests CoT and ToT prompting; evaluated on an Iranian online-broker SRS and NASA X-38 fault-tolerant specs; claims "more accurate and context-aware results" than baseline RAG but headline metrics were not retrievable; notes effectiveness "heavily relies on the quality and completeness of the input data" — [arXiv 2412.08593](https://arxiv.org/pdf/2412.08593); [Moonlight review](https://www.themoonlight.io/en/review/leveraging-graph-rag-and-prompt-engineering-to-enhance-llm-based-automated-requirement-traceability-and-compliance-checks)
- CTRAG (in-context retrieval for automated compliance checking): for GPT-4, precision ranged 71.91→62.07% and recall 85.33→72.00% from small to large chunks; "GPT-4o and Gemini Flash miss most Non-Compliant cases without further guidance" — [arXiv 2608.02472](https://arxiv.org/html/2608.02472)

- A 2026 CPS supplier guide recommends each non-conformance record cite "the specification clause breached, the revision, and a should-be versus is statement" — a useful output schema reference — [FleetRabbit supplier packaging compliance guide](https://fleetrabbit.com/article/supplier-packaging-compliance-for-manufacturing)

### Inferences
- The market gap is real: RM vendors have stopped at authoring-quality AI; the "supplier doc vs. spec with evidence" job is being done by construction/GovCon verticals and by hobby-scale OSS. A multi-discipline plant-engineering tool in this niche has no established incumbent.
- Independent accuracy evidence for clause-level verdicts clusters around precision 60–75% / recall 70–85% for general-purpose LLM+RAG, with the systematic failure mode being *missed non-compliance* (false "compliant"). The ctsm design choice of "0 false compliant" as the primary metric and "unverified → open/human review" is the correct safety posture.
- The best OSS patterns to copy: deterministic pre/post guardrails around one LLM call (ctsm), quote-verification against source text (ctsm), reverse checks for omitted obligations (CompChecker), an explicit "insufficient_evidence" verdict (CompChecker, Compliance_Checker), and multi-agent debate only for uncertain cases (AICCE).

### Gaps
- No head-to-head independent benchmark of Datagrid, Ichi, Document Crunch, Autodesk Assistant or GovDash for spec compliance was found; all accuracy figures are vendor-reported.
- Headline metrics for the Graph-RAG compliance paper (2412.08593) were not retrievable (arXiv blocked for direct fetch).
- No Anthropic/OpenAI-based startup specifically targeting *industrial equipment datasheet* compliance was found; SpecLens (AI equipment procurement) and DeepMechanix (ASME VIII vessel design from RFQ) are the nearest, both vendor-only sources.
- No independent accuracy data for Jama Advisor, Polarion Copilot, IBM RQA, ValiAssistant, QVscribe or Reqi REX.

## KQ2. What is the best practical architecture for clause-level compliance checking (extraction, matching, verdict, evidence, human review), and what accuracy is achievable?

### Takeaway
The literature and working prototypes converge on a staged pipeline: (1) deterministic parsing + atomic-requirement extraction with human curation, (2) hybrid retrieval (BM25 + embeddings, or graph-RAG over a requirement/standard graph) to pair each requirement with candidate evidence, (3) a schema-constrained LLM verdict with mandatory verbatim quotes, (4) programmatic quote verification and numeric/unit checks outside the LLM, (5) an explicit "insufficient evidence" state routed to human review. Reported achievable accuracy: atomic extraction ~44% exact semantic match / ~61% recall (agentic, unstructured input); requirement-quality defect detection is good for linguistic defects but poor for judgment-based ones (false-alarm medians 0.09–0.67 by criterion); contradiction detection ~99% accuracy/60% recall with formal-logic + LLM hybrid; clause-level verdicts P 0.6–0.75 / R 0.7–0.85 with LLM+RAG. Nothing published addresses units/tolerances for LLM compliance checking specifically.

### Cited Findings

**Requirement extraction into atomic requirements**
- Agentic LLM formalization from unstructured specs (arXiv 2604.18228): against manually built ground truth, exact semantic match for 43.6% of generated requirements, recall of ground-truth requirements 60.6%; 28 of 71 ground-truth requirements had no mapped generated requirement — [arXiv 2604.18228](https://arxiv.org/pdf/2604.18228)
- ReqEBench (requirement concern extraction benchmark): 2,721 requirements from 12 real-world industrial cyber-physical systems, built to stress long-range coreference and nested conditionals — [arXiv 2510.19237](https://arxiv.org/pdf/2510.19237)
- ReqGenX: empirical study of atomic decomposition, artifact regeneration and reconstruction for legacy SRS documents (findings not retrievable) — [arXiv 2607.16564](https://arxiv.org/pdf/2607.16564)
- Extracting formal specifications from documents with LLMs for automated testing (2025) — [arXiv 2504.01294](https://arxiv.org/pdf/2504.01294)
- Review of LLM-generated formal specifications: GPT-4o specs often preserve functional behaviour but frequently fail verification under a static verifier — [arXiv 2506.11874](https://arxiv.org/pdf/2506.11874)
- SLR of LLMs for RE (Zadenoori, Dąbrowski, Alhoshan, Zhao, Ferrari; arXiv 2509.11446, Sept 2025): 74 primary studies 2023–2024; focus has shifted to elicitation and validation; zero-shot 44%, few-shot 29%, RAG only 6%; GPT models in 90% of studies; 61% share code/prompts but shared datasets scarce; study count grew 136% in 2024 — [arXiv 2509.11446](https://arxiv.org/abs/2509.11446v1)
- A Frontiers in Computer Science systematic review (Mar 2025) covers LLMs across requirements and specification work including validation/QA — [Frontiers 2025](https://www.frontiersin.org/journals/computer-science/articles/10.3389/fcomp.2025.1519437/pdf)

**Requirement quality assessment (relevant to both extraction QA and "is this spec well-formed")**
- "Two Truths and A Lie?" (Shefa, Salado, Wach, Topcu; arXiv 2609.03230, Sept 2026): ten OpenAI/Anthropic models, five generations each, 100 runs, two requirement sets, five temperatures, against expert ground truth built on INCOSE quality criteria. False-alarm rate medians by criterion: conformance 0.67, ambiguity 0.33, singularity 0.18, necessity 0.17, completeness 0.09. Models were more reliable on linguistically explicit issues (ambiguity, verifiability) and poor on issues needing systems-engineering judgment (correctness, necessity, boundedness). Conclusion: not suitable for autonomous quality evaluation; can assist experts — [arXiv 2609.03230](https://arxiv.org/abs/2609.03230)

**Conflict / contradiction detection**
- Gärtner & Göhlich (DESIGN 2024): hybrid formal logic + GPT-3 contradiction detection on a real electric-bus project achieved 99% accuracy and 60% recall — [Proceedings of the Design Society 2024](https://www.cambridge.org/core/services/aop-cambridge-core/content/view/C7D7E69A58BBC2BC6054AF0BB972A3E1/S2732527X24002074a.pdf/towards-an-automatic-contradiction-detection-in-requirements-engineering.pdf)
- ALICE (Automated Logic for Identifying Contradictions in Engineering; Springer, DOI 10.1007/s10515-024-00452-x — the s10515 prefix is *Automated Software Engineering*, journal name not confirmed in results): decision tree of seven questions over controlled-natural-language requirements; detected 60% of all contradictions, "clearly outperforming an LLM-only approach" — [Springer article](https://link.springer.com/article/10.1007/s10515-024-00452-x)
- "Automating the Detection of Requirement Dependencies Using LLMs" (2026) — [arXiv 2602.22456](https://arxiv.org/pdf/2602.22456)
- AraREQ (LREC 2026): 27K Arabic requirement pairs for conflict detection; benchmarks four LLMs zero/few-shot — [LREC 2026](https://aclanthology.org/2026.lrec-1.553.pdf)
- Polarion Copilot "Consistency Check" (linked work items) and Valispace "finding inconsistencies between requirements" are the shipped commercial equivalents, without published accuracy — [Polarion X 2512](https://blogs.sw.siemens.com/polarion/polarion-x-2512-whats-new-and-noteworthy/); [Valispace AI blog](https://valispace.com/?p=19487)

**Requirement-to-evidence matching, chunking, retrieval**
- CTRAG shows chunk size materially moves precision/recall (GPT-4: P 71.9→62.1%, R 85.3→72.0% from small to large chunks) — [arXiv 2608.02472](https://arxiv.org/html/2608.02472)
- Graph-RAG compliance paper argues graph retrieval over regulations+standards+SRS outperforms flat RAG, and that "difficulties in maintaining context across extensive documents can make LLM analysis incomplete" — [arXiv 2412.08593](https://arxiv.org/pdf/2412.08593)
- GraphRAG dual-path structural diffusion retrieval (DSDR) for requirement–code trace-link recovery: with GPT-4o validation yields higher precision than the strongest LLM baseline, with recall/precision trade-offs by project — [Information 17(6):541](https://doi.org/10.3390/info17060541)
- A GraphRAG vendor claims "60% → over 90% accuracy" moving from RAG to GraphRAG — marketing, no methodology — [Graphwise blog](https://graphwise.ai/blog/reducing-risk-and-rework-how-graphrag-delivers-roi-in-compliance-and-legal-workflows/)
- CompChecker chunks tables row-by-row and runs reverse checks (policy→supplier) so omissions appear; ctsm uses BM25 over page-mapped PDF chunks and verifies every quoted span against its source — [CompChecker](https://github.com/Aaryan-Chokshi/CompChecker); [ctsm](https://github.com/epifaneia/ctsm)

**Verdict, evidence and human review**
- ctsm: verdict enum taken from the customer's own ReqIF status field; evidence must include document/page/section; unverified → stays open and flagged — [ctsm](https://github.com/epifaneia/ctsm)
- CompChecker: five-valued rating incl. insufficient_evidence/not_applicable, extent %, uncalibrated confidence, overall needs_review, and an auto-generated supplier clarification questionnaire tied to matrix rows — [CompChecker](https://github.com/Aaryan-Chokshi/CompChecker)
- AICCE: unanimous section-agent "Yes" accepts; any disagreement triggers structured debate that surfaces clause-level justification — [arXiv 2604.03330](https://arxiv.org/abs/2604.03330)
- Human-in-the-loop middleware paper: compliance *decisions* should remain in deterministic logic for traceability and reproducibility, with LLMs confined to extraction — [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S1474034626008049)
- Datagrid explicitly positions its agent as pre-screening support that "does not make approval decisions or replace the PE's stamp" — [Datagrid](https://www.datagrid.com/agents/summary-spec-submittal-agent)

**Units and numeric tolerances**
- QVscribe performs terminology and *unit consistency* checks as part of requirement scoring — [QRA FAQ](https://qracorp.com/faqs/)
- Ontology-based process-model consistency verification (arXiv 2506.16087) implements knowledge-graph checks for missing data bindings, *unit mismatches*, and incomplete parameter definitions (manufacturing, not plant-wide) — [arXiv 2506.16087](https://arxiv.org/pdf/2506.16087)
- A manufacturing (G-code) parameter-extraction study reports three frontier models each >90% tolerance-based accuracy on structured extraction, lowest MAPE 3.50% — demonstrates numeric extraction with tolerance scoring as an evaluation method, but not for datasheets — [arXiv 2605.03328](https://arxiv.org/pdf/2605.03328)
- SpecLens (vendor) claims "98%+ extraction accuracy" for pulling specs from vendor documents with unit/terminology normalisation and side-by-side comparison matrices — unverified — [SpecLens blog](https://www.speclens.ai/blog/ai-equipment-procurement-guide)
- Multimodal LLM vs traditional OCR for table extraction (ACL XLLM 2025) is the nearest published benchmark for datasheet tables — [ACL Anthology 2025.xllm-1.2](https://aclanthology.org/2025.xllm-1.2/)
- IC-footprint understanding from datasheets: GPT-4o scored low; fine-tuned LLM4-IC8K reached 71.6% IoU (diagram geometry, not parameters) — [arXiv 2508.03725](https://arxiv.org/html/2508.03725v1)

### Inferences
- Treat the LLM as an *extractor and matcher*, not a judge of numbers: parse numeric values + units into a typed structure (quantity, unit, tolerance, condition) and compare with code (e.g., Pint-style unit conversion), reserving the LLM for text-only clauses. This follows directly from the finding that deterministic logic is needed for traceable verdicts and from the absence of any published LLM units/tolerance benchmark.
- Expect a recall ceiling around 60–85% for any single-pass LLM stage (extraction, contradiction, verdict); design for coverage via reverse checks, coverage dashboards (requirements with no evidence), and mandatory human sign-off on "not evidenced."
- False-alarm behaviour differs sharply by criterion (0.09 completeness vs 0.67 conformance), so per-rule confidence thresholds and per-rule human-review routing are justified rather than one global threshold.
- Chunk size and table handling are first-order tuning levers (CTRAG, CompChecker); row-level table chunking is the right default for datasheets.

### Gaps
- No published benchmark exists for LLM handling of engineering units/tolerances in compliance checking; no datasheet-parameter-extraction accuracy benchmark for industrial equipment was found.
- Full-text details (datasets, metrics) of 2412.08593, 2604.18228, 2607.16564 could not be fetched.
- No study found evaluating compliance checking against ASME/API/IEC-type engineering standards (as opposed to building codes, protocols or legal text).

## KQ3. How should a tool help write good equipment requirement specifications, and what open-source scaffolding (StrictDoc, Doorstop, Sphinx-Needs) could be reused?

### Takeaway
"Good requirement" is well codified: ISO/IEC/IEEE 29148:2018 (individual + set characteristics), INCOSE Guide to Writing Requirements v4 (1 July 2023; 14 characteristics C1–C14 and ~40 rules), and EARS (five syntactic patterns from Rolls-Royce, RE'09). Every commercial AI writing assistant (Jama Advisor, Polarion Content Validation, IBM RQA, Reqi REX, QVscribe) is essentially a rule-checker against these; a new tool should score against the same rules and emit EARS-shaped text. For equipment specs there is no verified LLM datasheet generator; the only evidence for AI-generated equipment specs is vendor marketing (SpecLens, DeepMechanix), plus one P&ID-design paper that constrains LLMs with engineering rules and tool-based equipment selection. The OSS scaffolding is healthy: StrictDoc (Apache-2.0, 420 stars, v0.30.3 Oct 2026, ReqIF+Excel import), Doorstop (LGPLv3, 686 stars, v3.2), Sphinx-Needs (MIT, 314 stars, needs.json exchange v1.1.0 Oct 2026), the strictdoc-project/reqif library, and BMW's TRLC; OpenReq and Eclipse Capra are dormant.

### Inferences
- The authoring assistant should implement the INCOSE GtWR v4 rule set and EARS patterns as *explicit, named rules* (as Jama, Polarion and Reqi do) rather than free-form LLM critique; the 2026 benchmark shows LLM judgment is weakest exactly where rules are least mechanical (necessity, correctness), so those should be flagged for human review, not auto-scored.
- For equipment specs, the viable path is template-driven generation: a property schema per equipment class taken from IEC CDD/ECLASS/CFIHOS/AAS "Technical Data" (open, CC-BY or membership-licensed dictionaries), filled from a project knowledge base, with LLM used for prose and rationale and with each parameter cross-referenced to the governing standard clause by *identifier* (see KQ5).
- StrictDoc is the most natural backbone (Apache-2.0, ReqIF+Excel import/export, UIDs, relations, PDF/HTML, active monthly releases); Sphinx-Needs' needs.json/ub-needs-exchange is a second interchange target; Doorstop's YAML-in-Git is simpler but has no ReqIF.

- No academic or OSS project found that generates equipment requirement specifications from a knowledge base with standards cross-references.
- Doorstop's current import/export format list beyond YAML/HTML/Markdown was not confirmed.

## KQ4. Which ontologies/standards for engineering data are worth adopting early to support systems integration across disciplines (interface management, ICDs, cross-discipline conflicts)?

### Takeaway
For plant engineering the stack with the most momentum and open artefacts is: ISO 15926-4 RDL + ISO 15926-6:2024 rules (confirmed current 2026), its OWL upper ontology now migrating from ISO/TR 15926-14 to the Industrial Data Ontology (ISO 23726-3, still in development) hosted by POSC Caesar with SPARQL endpoints cross-referencing CFIHOS and DEXPI; CFIHOS (IOGP JIP36) for equipment classes/properties and handover; DEXPI for P&IDs (pyDEXPI, DEXPI 1.3, makes it programmable); IEC 61360/IEC CDD + ECLASS via Asset Administration Shell submodels for vendor datasheets; and SysML v2 (OMG adopted 30 June 2025; spec PDFs updated Mar 2026 for ISO submission) for requirements, typed ports/interfaces, connections and verification cases. Published evidence on *AI-driven* cross-discipline conflict detection in plants is thin: KG-based consistency checks (unit mismatches, missing bindings) exist for manufacturing, and ICD studies show hardware-side and timing details are routinely omitted.

- Adopt early: (1) a tag/identifier spine (ISO 15926/CFIHOS class IDs for plant objects; IEC CDD/ECLASS IRDIs for properties and units) so every requirement parameter is typed; (2) DEXPI via pyDEXPI for P&ID-derived process requirements (AGPL is a licensing consideration for a commercial product); (3) SysML v2 textual notation for interface definitions (`interface def`, `connection def`, verification cases), since it is now an adopted OMG standard with an open pilot implementation and API; (4) IDO/ISO 23726 as the upper ontology, tracked but not depended on until published.
- Cross-discipline conflict detection (electrical load vs heat rejection, structural load vs equipment mass) is tractable as *typed-quantity rules over a KG* (SHACL/OWL reasoner or SQL constraints), not as an LLM task; the literature supports KG consistency checking for units/bindings but none of it is plant-wide yet, so this would be novel.
- ICD tooling should force the fields the 2022 study found missing (hardware side, timing/state) into the template.

## KQ5. What are the legal/IP constraints on ingesting standards (ASME, API, IEC, ISO, IEEE, NFPA, ASTM) into a knowledge base, and how do tools reference them without redistributing text?

### Takeaway
Two separate constraints apply. (1) Copyright/fair use: US courts have held that *non-commercial* posting of standards *incorporated by reference into law* is fair use (D.C. Cir., ASTM v. Public.Resource.Org, Sept 2023; Third Circuit, ASTM v. UpCodes, 7 Apr 2026, preliminary and precedential), and the Fifth Circuit (Veeck) held such standards lose copyright protection on incorporation; none of this covers commercial use or standards not incorporated into law (most ASME/API/IEC content). (2) Contract/licence terms: ISO's Online Browsing Platform terms expressly prohibit training/fine-tuning language or generative-AI models on its content and opt out of the EU TDM exception (Art. 4, Directive 2019/790); IEEE licences prohibit using licensed content to develop/train AI tools or storing it within any AI tool; ASHRAE prohibits entering any publication content into any AI tool; SFS (Finland) bans AI training and even "using generative AI tools to analyse standards." ASME and API terms were not retrievable. Practical pattern used by tools: store only clause identifiers, titles, user-supplied excerpts and derived structured parameters; retrieve licensed text at query time from the user's own subscription (Accuris/Techstreet, IHS) rather than redistributing.

### Cited Findings
- CRS report (Sept 2023): courts have not reached consensus on whether technical standards remain copyrighted after incorporation into law; the Fifth Circuit rejected copyright protection for incorporated standards outright, while the D.C. Circuit resolved on fair use — [CRS R47656](https://www.everycrsreport.com/files/2023-09-26_R47656_06eea6d3ebb0acb711bfcf09a27e744b1579e96e.html)
- D.C. Circuit (Sept 2023, ASTM v. PRO II): non-commercial use of standards incorporated by reference into law is fair use; relied in part on Georgia v. Public.Resource.Org (2020) — [Husch Blackwell](https://www.huschblackwell.com/newsandinsights/dc-circuit-court-holds-non-commercial-use-of-industry-standards-incorporated-into-law-is-fair-use); [PHCPpros](https://www.phcppros.com/articles/18733-copyright-infringement-ruling)
- Third Circuit (7 Apr 2026, ASTM v. UpCodes, precedential): affirmed denial of preliminary injunction; UpCodes' posting of incorporated building codes likely fair use; use is transformative because its purpose is informing the public about binding law rather than best practice; a work need not be altered to be transformative; laws treated as "facts at the periphery of copyright"; market impact likely limited; UpCodes did not charge for the codes; case continues on the merits — [LawNext](https://www.lawnext.com/2026/04/third-circuit-rules-that-upcodes-publication-of-incorporated-building-standards-is-likely-fair-use.html); [EFF](https://www.eff.org/deeplinks/2026/04/another-court-rules-copyright-cant-stop-people-reading-and-speaking-law); [Reed Smith](https://www.reedsmith.com/our-insights/blogs/viewpoints/102mpa3/when-standards-become-law-fair-use-kicks-in-implications-of-recent-third-circui/); [Bloomberg Law](https://news.bgov.com/ip-law/third-circuit-lets-site-keep-building-codes-online-during-suit)
- ISO OBP Terms of Use bar training or fine-tuning language or generative-AI models on ISO content and expressly opt out of the EU TDM exception under Article 4 of Directive (EU) 2019/790 — [ISO OBP Terms](https://www.iso.org/home/store/iso-obp-terms.html)
- ISO internal guidance (reported via a WG21 mailing-list link) tells ISO staff: "Do not use images or text created by generative AI in any ISO content"; WG21 members state copyright in the C++ standard sits with ISO and training-rights questions go through national bodies — anecdotal — [isocpp std-proposals, May 2025](https://lists.isocpp.org/std-proposals/2025/05/13883.php); [isocpp std-proposals, June 2026](https://lists.isocpp.org/std-proposals/2026/06/18530.php)
- IEEE Xplore API terms limit use to non-commercial educational/research purposes within the licensee's institution; IEEE licence text prohibits using licensed products with AI tools to build substitutes, creating derivative works, and "expressly prohibits use of the licensed content for developing or training AI tools and prohibits storing or retaining it within any AI tool" — [IEEE API Terms](https://developer.ieee.org/API_Terms_of_Use2); [Unitec IEEE copyright guide](https://guides.unitec.ac.nz/copyright/vc/ieee); [IEEE CS Digital Library terms (no robots/agents for systematic download)](https://computer.org/digital-library/terms-of-use)
- SFS (Finnish standards body) prohibits using standards to train or develop AI and prohibits using generative-AI tools to analyse standards — [SFS copyright page](https://store.sfs.fi/en/copyright)
- ASHRAE Digital Collections policy "prohibits the entry of content from any ASHRAE publication or related ASHRAE IP into any AI tool" — [ASHRAE Digital Collections](https://www.ashrae.org/technical-resources/bookstore/ashrae-digital-collections)
- ASME conference policy pages state "Generative Artificial Intelligence Use Prohibited" (for meetings/papers; the ASME Digital Collection terms were not retrieved) — [ASME IMECE AI policy](https://event.asme.org/IMECE/Policies/Artificial-Intelligence)
- ASM International (not ASME) EULA defines AI broadly and lists prohibited AI uses — illustrates the direction of engineering-society licences — [ASM Data Ecosystem EULA](https://www.asminternational.org/asm-data-ecosystem-eula)
- Standards are sold through resellers (SFS, SNV, VDE, BSI, Accuris) and full text is paywalled; e.g., ISO/IEC/IEEE 29148 — [VDE preview](https://www.vde-verlag.de/iec-normen/preview-pdf/info_isoiecieee29148{ed2.0}en.pdf); Accuris markets the 2025 ASME BPVC with "Your AI Is Only as Smart as Your Data" webinars, indicating licensed-data feeds for AI as the reseller model — [Accuris 2025 BPVC](https://accuristech.com/2025-asme-boiler-code/)
- Open alternatives: IDTA AAS specs are CC-BY-4.0 — [IDTA 01003-a-3-1-1](https://industrialdigitaltwin.org/wp-content/uploads/2025/08/IDTA-01003-a-3-1-1_AAS-Specification_Part3a_DataSpecification.pdf); IEC CDD is a public online dictionary — [IEC CDD](https://tc3.iec.ch/tc-activity/common-data-dictionary-cdd/); PCA RDS exposes SPARQL endpoints — [PCA RDS](https://rds.posccaesar.org/features/); OMG ReqIF and SysML v2 specs and OASIS OSLC are freely downloadable — [OMG ReqIF](https://www.omg.org/spec/ReqIF/1.2/Beta1); [SysML-v2-Release](https://github.com/Systems-Modeling/SysML-v2-Release); [OASIS OSLC RM 2.1](https://www.oasis-open.org/?p=5068)
- A US GSA acquisition clause (GSAR 552.239-7001, effective 19 Oct 2026) requires contractors to exercise due diligence over LLM developers/providers and flow requirements down — relevant if the tool is sold to US federal contractors — [Winston Taylor](https://www.winstontaylor.com/insights/gsa-s-new-ai-contracting-clause-compliance-considerations-beyond-data-security); [Federal Register 2026-12205](https://www.federalregister.gov/documents/2026/06/17/2026-12205/general-services-acquisition-regulation-acquisition-of-information-and-communication-technology)

### Inferences
- The fair-use line does not help a commercial plant-engineering tool: it is limited to non-commercial republication of law-incorporated standards; ASME BPVC, API 610/650, IEC 61511 etc. are mostly not incorporated into law in the relevant jurisdictions, and the ingest would be commercial. Licence terms (ISO, IEEE, ASHRAE, SFS) are now explicitly anti-AI-ingestion, so embedding or fine-tuning on purchased PDFs likely breaches contract regardless of copyright outcome.
- The defensible architecture is "reference, don't redistribute": the knowledge base stores standard ID + edition + clause number + clause title (facts, uncopyrightable), the *user's own* structured parameter extractions, and pointers; at check time the tool asks the user to supply their licensed copy (or integrates a reseller API such as Accuris) and processes it ephemerally under the user's licence. For dictionaries, use CC-BY/open sources (IDTA, IEC CDD, PCA RDS, CFIHOS via IOGP membership) as the semantic layer.
- The ASHRAE/SFS wording ("entering content into any AI tool", "using generative AI tools to analyse standards") is broad enough to arguably prohibit even user-side LLM processing of licensed text; this is an unresolved commercial/legal risk that needs counsel and possibly bilateral licences with SDOs.

### Gaps
- ASME Digital Collection and API Publications terms on AI/TDM were not retrievable.
- No source found on whether SDOs (ASME, API, IEC) offer AI/TDM licences to tool vendors; Accuris' marketing suggests reseller-mediated AI data deals exist but details were not found.
- No non-US case law (EU/UK) on standards and AI ingestion was researched.

## KQ6. Which interchange formats should the tool support (ReqIF, DOORS exports, Excel compliance matrices, OSLC)?

### Takeaway
ReqIF 1.2 (OMG; 1.2 beta Dec 2015, formal version current; ProSTEP iViP implementation guide v1.10, Jan 2024) is the de facto file exchange between DOORS, DOORS Next, Polarion, Jama, Capella and StrictDoc, but round-tripping is lossy and tool-flavoured; OSLC RM 2.1 (OASIS Standard, 21 June 2021) is the live-link API supported by DOORS/DOORS Next and implemented in Eclipse Lyo (6.0.1, EPL-2.0); Excel remains the lingua franca of compliance matrices (GovDash, Loopio, QVscribe, StrictDoc, sltoo, reqif2excel). Supporting ReqIF import/export (via strictdoc-project/reqif or reqifsharp), OSLC RM consumer, Excel/CSV, and Sphinx-Needs needs.json covers the field.

### Cited Findings
- ReqIF adopted by OMG in 2011; XML-based; 1.2 Beta1 dated Dec 2015 with the formal version "the one to follow for compliance"; Visure (Aug 2026) calls it the common foundation for interchange among DOORS and Polarion — [OMG ReqIF 1.2](https://www.omg.org/spec/ReqIF/1.2/Beta1); [Visure ReqIF guide](https://visuresolutions.com/alm-guide/reqif)
- ProSTEP iViP ReqIF Implementation Guide v1.10 (Jan 2024) covers questions the OMG standard leaves open — [ProSTEP guide](https://www.prostep.org/fileadmin/prod-download/ProSTEP_iViP_ImplementationGuide_ReqIF_V1-10_aw.pdf)
- Round-trip losses: importing ReqIF into DOORS and re-exporting lost fields (2020 report using OSLC and Lyo); DOORS Next cannot preserve artifact reuse through ReqIF import (IBM Ideas entry) — [IBM Community](https://community.ibm.com/community/user/discussion/export-reqif-via-dwa); [IBM Ideas ENGRMDN-I-1320](https://ibm-ai-apps.ideas.ibm.com/ideas/ENGRMDN-I-1320)
- StrictDoc: ReqIF support is tool-specific; 0.30.3 fixed cross-type Parent relations on import; Excel import declares Parent relations — [StrictDoc FAQ](https://strictdoc.readthedocs.io/en/latest/strictdoc_02_faq.html); [StrictDoc releases](https://github.com/strictdoc-project/strictdoc/releases)
- strictdoc-project/reqif library: tools differ in attribute order and schema completeness; parser tolerant of invalid files; official XSD validation off by default — [reqif repo](https://github.com/strictdoc-project/reqif)
- Other ReqIF implementations: STARIONGROUP/reqifsharp (C#, 34 stars, active Oct 2026) and reqifviewer; ebroecker/pyreqif (33 stars, 2024); IBM/ELM-Python-Client (50 stars; OSLC query, ReqIF import/export, reporting for IBM ELM — not an IBM product); cosmindxu/reqif2excel; Capella ReqIF import add-on; STARIONGROUP/DEH-REQIF converts ECSS-E-TM-10-25 requirements to ReqIF — [GitHub topic: reqif](https://github.com/topics/reqif)
- OSLC Requirements Management 2.1 became an OASIS Standard on 21 June 2021; three parts (spec, vocabulary, constraints); RESTful interfaces for requirements and collections — [OASIS announcement](https://www.oasis-open.org/?p=5068); [OSLC RM 2.1 vocabulary](https://docs.oasis-open.org/oslc-domains/oslc-rm/v2.1/cs01/part2-requirements-management-vocab/oslc-rm-v2.1-cs01-part2-requirements-management-vocab.html); [open-services.net RM](https://open-services.net/spec/rm/latest)
- DOORS Next is an OSLC provider for the RM domain and a consumer of other domains; classic DOORS also shares data via OSLC; IBM reports customers worldwide connecting DOORS/DOORS Next via OSLC (Mar 2025) — [IBM OSLC docs](https://www.ibm.com/support/knowledgecenter/SSYMRC_7.0.2/com.ibm.rational.rrm.help.doc/topics/r_rm_oslc_services.html); [IBM Community thread](https://community.ibm.com/community/user/discussion/doors-requirements-lifecycle)
- Eclipse Lyo: Java OSLC SDK (core, client, TRS server/client, store, validation, domains), EPL-2.0, 26 stars, 2,041 commits, Javadoc badge 6.0.1.Final; Lyo ≤4.1.0 vulnerable to CVE-2021-41042 on untrusted RDF/XML — [Eclipse Lyo](https://github.com/eclipse/lyo)
- Excel as compliance-matrix medium: GovDash/GovEagle/Loopio output matrices; QVscribe interfaces with Excel; sltoo adds Excel import/export to rmtoo; StrictDoc exports Excel — [GovDash](https://www.govdash.com/blog/old-vs-ai-compliance-matrix-comparison); [QRA FAQ](https://qracorp.com/faqs/); [sltoo](https://pypi.org/project/sltoo/25.0.4); [StrictDoc docs](https://strictdoc.readthedocs.io/_/downloads/en/latest/pdf/)
- Sphinx-Needs needs.json is now versioned as "ub-needs-exchange" (v1.1.0, Oct 2026) and rejects files newer than the supported format version — [sphinx-needs releases](https://github.com/useblocks/sphinx-needs/releases)
- ctsm demonstrates writing compliance verdicts *back into* the customer's ReqIF (Polarion export) with evidence in Rationale fields — [ctsm](https://github.com/epifaneia/ctsm)

### Inferences
- Minimum viable interchange: ReqIF 1.2 import/export with per-tool profiles (DOORS/DOORS Next, Polarion, Jama), Excel/CSV compliance-matrix import/export, and needs.json; OSLC RM 2.1 consumer for live linking into DOORS Next is a second-phase item given its Java-centric ecosystem.
- Writing verdicts back into the originating ReqIF (ctsm pattern) is the lowest-friction way to return results to customers who live in Polarion/DOORS.
